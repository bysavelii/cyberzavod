# Publishing a session recording

On the site, a prompt is a message to the model that received it: "human → model", the goal is visible at once, the requirements expand. What is shown is not how the prompt was typed but the clean prompt: the way a human who had time would have written it. The foreman in the factory is the human: they walk to the stations themselves, state the task, and listen to the answer. Next to the prompts you hear the workers' messages: they talk to each other when handing over a part and sending it back, take assignments, and give the result and the report to the foreman — a single line above the speaker, the full text is in the recording. When the automation stops and waits for the human (an answer to the model's question, approval of the plan, a call after reworks, a call by the stop hook), their word goes not as a prompt but as an intervention: the foreman walks out to the station where the work stands and states their decision, and in the recording it is a separate event. The original text (`said`) stays in the draft outside git and does not reach the site.

## Steps

1. `{{cli}} draft` — a draft from the most recent session log; for another log — `{{cli}} draft {{raw}}/<session>.jsonl`. The draft is placed in `{{drafts}}/<id>.json`. The model of a prompt (`model`) is detected automatically from the session transcript, the messages (`draft_message`) — from the transcripts of the session and the stations. The edits from the previous draft of the same session are carried over, and the command prints what still awaits editing. If you rebuild the draft of an old log, a prompt that is now recognized as an intervention (`plan_review` or `rework_limit`) becomes a `draft_intervention`: its `goal` and `requirements` are not carried over, while `line` and `text` await editing, so it will again appear in "awaiting editing". If the session ran one task, there is one build (`builds[0]`) — go to step 2. If there are several tasks, first split the builds by the section "Several tasks in one session".
2. The header of every build in `builds`: `project`, `harness`, and `workflow` usually come from the log. If they are empty (the hooks were connected in the middle of the session), fill them in from `.cyberzavod/project.json` of the repository where the task ran: `project` — `projectId`, `harness` and `workflow` — the fields of the same name. Fill in yourself the `title` and `language` of every build and, for every `draft_prompt` event, the `goal` and `requirements` fields by the rules below. `language` is the language in which the human wrote the build's prompts, as an ISO 639 code: `ru`, `en`. The recording is not translated: the title, prompts, messages, and interventions are written in that language. Do not change the fields `said`, `model`, `build`, `run`, `reason` and the other events.
3. Hand the messages and interventions to the `recording-editor` agent: it will fill in `line` and `text` for all `draft_message` by the message rules and for all `draft_intervention` by the intervention rules. Do not edit them yourself.
4. Show the human a table of builds (if there is more than one) and, for each build, the title and three tables. Builds: `id` · project · version · language · title · runs. Prompts: time · as written (briefly) · goal · requirements. Messages: time · route · `source` · line · start of the text. Interventions: time · reason · as said (briefly) · line · start of the text. Wait for explicit approval. If there are comments, fix them (messages and interventions — again through `recording-editor`) and show the tables again.
5. `{{cli}} publish` — publishes all builds of the most recent draft; `{{cli}} publish --build <build id>` — only one (the others may not be ready), `--draft <file>` — another draft. Publishing checks the format and searches for addresses and keys, then writes the session recording `sessions/<build id>.json` to the project journal. If even one of the selected builds is not ready, nothing is written: fix what is named, do not bypass the check. If something is found that must not be shown, rewrite that place.
6. If the journal is in the project's repository, run the project checks and commit the recording by the commit rules from AGENTS.md.
7. Share to the gallery. The human never types commands: you run every step below yourself. The lines quoted below are the English output of the CLI; it may print them in the human's language, so go by the meaning.
   1. Ask the human with `AskUserQuestion`: "Send the recording to your gallery on cyberzavod.com?" If there are several builds, name their ids and ask once for all of them. If the human declines, stop: the recording stays in the journal, and it can be sent later with `{{cli}} share <build id>`.
   2. For each build run `{{cli}} share <build id>`. Show the human the address from the `link: <url>` line. Sharing a recording again replaces it, and the link stays the same.
   3. If `share` asks to sign in (`not signed in`, `the server did not accept the token`, or a corrupted credentials file), run `{{cli}} login` in the background: it waits for confirmation until the code expires, which is longer than a foreground command may run. Right away read the output of the background command, without waiting for it to finish, until the line `Open <url> and enter the code <code>` appears. Show the human the address and the code and ask them to confirm on that page. Once the human confirms, the command finishes on its own: check its output for `signed in: <login>` or for an error, then run `{{cli}} share <build id>` again for the same build and go on with the rest. If sign-in fails (the code expired or was denied) or the human does not want to sign in, stop and name the commands to continue: `{{cli}} login`, then `{{cli}} share <build id>`.
   4. If `share` fails with `the gallery already holds the maximum number of recordings`, show the human the recordings it listed (`id  title`) and ask which one to remove, or none. Ask in an ordinary message, not with `AskUserQuestion`: the list plus "none" may not fit into `AskUserQuestion`, which offers at most four options. Remove nothing unless the human names a recording explicitly. When they do, run `{{cli}} unshare <chosen id>`, then `{{cli}} share <build id>` again for the same build, and go on with the rest. If they choose none, stop and name the commands to continue: `{{cli}} unshare <id>`, then `{{cli}} share <build id>`.
   5. Any other error: show it as printed and stop. The recording stays in the journal.
   6. If `share` printed `the gallery is closed: the recording is visible only by this link`, after all the builds are shared, ask once with `AskUserQuestion` whether to open the gallery. Explain that an open gallery has its own page that anyone with its link can see, for example from the README badge, while the recording links work either way. If the human agrees, run `{{cli}} gallery --public` and show the human the `Gallery page:` address and the `README badge:` line. If not, say that `{{cli}} gallery --public` opens the gallery later and prints the badge. If the gallery is already open, do not show the badge: `{{cli}} gallery` prints it on request.
