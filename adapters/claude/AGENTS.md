# Адаптер Claude Code (adapters/claude)

Первый адаптер агента. Две работы: собрать из harness и конфига проекта файлы, которые понимает Claude Code (`src/generate/`), и записать сессию Claude Code в журнал проекта (`src/capture/`, `src/hooks/`, `src/commands/`). Ядро и CLI о Claude не знают; всё, что знает о нём, — здесь.

Общая часть с другими адаптерами вынесена в `packages/adapter-kit`: отметки и владение файлами, план синхронизации и отключения (`planSyncFiles`, `applySyncPlan`, `plannedDisconnectFiles`, `applyDisconnect`), манифест `.cyberzavod/generated.json` (`manifest.ts`), сборка и слияние обработчиков хуков (`hookCommand`, `mergedHooks`, `inspectHooks`), подстановки шаблонов, таблица этапов и абзацы рабочих правил, поиск проекта (`findProjectId`, `newestFile`) и `CLI_COMMAND`/`pinnedCliCommand` (`cli-command.ts`), `KitError` и каталог `KIT_MESSAGES`, а также весь черновик и публикация записи сессии (`to-draft.ts`, `draft.ts`, `builds.ts`, `leaks.ts`, команды `draftSession` и `publishSessions`, чтение транскриптов; тексты правил записи — `templates/` кита). Ниже они описаны там, где Claude на них опирается; в самом адаптере остаётся то, что знает только Claude: модели и инструменты ролей, формат `.claude/settings.json` и его запреты, привязка хуков и разбор транскриптов Claude Code.

## Генератор (`src/generate/`)

- `claude.ts` — что адаптер знает о Claude: ведёт только `anthropic`/`claude` (другой агент этапа — `GenerateError`, наследник `ClaudeError`), модели по умолчанию по этапу (постановка и ревью — `opus`, код и проверки — `sonnet`), `effort` по этапу, модель второй доработки, инструменты роли по её доступу (`read` — без правки).
- `files.ts` — чистые тексты: корневой `CLAUDE.md` (отметка генерации, маршрут процесса, проверки проекта, принципы harness с `always-on` и ссылка на скилл `principles` с остальными, `@AGENTS.md`), `CLAUDE.md` с одним `@AGENTS.md` рядом с каждым вложенным `AGENTS.md`, агент `.claude/agents/<роль>.md` на каждый этап процесса с ролью (текст скилла этапа и принципы, которых нет в `CLAUDE.md`: роль стартует с задания и скилл сама не открывает), скиллы harness в `.claude/skills/<имя>/` как есть (`harnessSkillFiles` кита) с полем `user-invocable: false` — человек начинает работу с `/feature`, а модель открывает скиллы сама, скилл `/feature` (таблица этапов, правила ведущего — инструкции скилла `harness/skills/feature/`, тексты этапов без роли) и из шаблонов `templates/` — скилл `/setup` (после `init` заполняет заглушки заготовки AGENTS.md сведениями о проекте и один раз запускает `verification.commands`; неверную команду правит в конфиге только с согласия человека), скилл `/publish-recording` и агент `recording-editor`. Подстановки шаблонов — `{{generated}}`, `{{cli}}`, `{{raw}}`, `{{drafts}}`, `{{todo}}` (отметка заглушки `RULES_TODO_MARK` из ядра); в скилле записи и у редактора ещё `{{recordingRules}}` и `{{recordingEditor}}` (общие куски кита, `templates/recording-rules.md` и `recording-editor.md`) и термины агента `{{feature}}` (`/feature`), `{{publishSkill}}`, `{{interventionWords}}` (`RECORDING_TERMS` в `files.ts`); неизвестная — ошибка. Тексты в `.claude/` этого репозитория не меняются от того, что общие куски переехали в кит: это проверяет `generate/files.test.ts` и `sync --check`. Шаблоны — тексты инструмента, не harness: они английские, могут называть `{{cli}}`, `.cyberzavod/project.json` и инструменты Claude Code, но не то, что относится только к этому репозиторию.
- `settings.ts` — хуки адаптера в `.claude/settings.json` проекта: свои обработчики (их команда запускает пакет через npx; узнаются по началу команды с любой версией и по `LEGACY_TOOL_FILE` прежних версий) заменяются, чужие и прочие настройки остаются, запреты адаптера дописываются без повторов. `adapterHooks(версия)` собирает команду хука: `npx -y --prefer-offline --fetch-retries=0 --prefix "$CLAUDE_PROJECT_DIR" cyberzavod@<версия harness из конфига> hook <имя> || <запасной путь>`. `--prefer-offline` берёт пакет из кэша без обращения к registry (иначе без сети npx ждёт минуту), `--fetch-retries=0` роняет запуск без кэша и сети сразу, `--prefix` от `$CLAUDE_PROJECT_DIR` находит пакет в `node_modules` проекта из любого подкаталога. Запасной путь срабатывает на любой ненулевой код: у `record` и `turn-start` это `true` (запись молча пропускается), у `stop` — `echo` JSON с `systemMessage`, агент отпускается, человек видит, что проверки пропущены. Поэтому остановка возвращает агента к работе не кодом 2, а JSON-решением `{"decision":"block","reason":…}` с кодом 0: код 2 запасной путь принял бы за «npx не запустился» и снял блокировку. Синтаксис POSIX: на Windows Claude Code запускает хуки через Git Bash, PowerShell не поддерживается.
- `inspect.ts` — `inspectClaudeHooks(корень, версия)`: читает `.claude/settings.json` и отвечает, стоят ли хуки адаптера (`inspectHooks` из `settings.ts`: `installed`, `missing`, `otherVersion` со списком версий — прежний вшитый CLI называется `LEGACY_TOOL_FILE`, `incomplete` со списком событий); нет файла — `missing`, не JSON, не объект или `hooks` не того вида — `unreadable` с диагностикой. Ничего не пишет; им пользуется `cyberzavod doctor`.
- `sync.ts` — ввод-вывод: находит проект, получает harness и шаблоны от CLI (`ClaudeInstallation`), ищет `AGENTS.md` (без скрытых каталогов, `node_modules` и журнала), сравнивает с диском. Файл с отметкой `GENERATED_MARK` или прежней русской `LEGACY_GENERATED_MARK` (версии до 0.8.0) генератор перезаписывает и удаляет, если он больше не нужен; файл человека на месте своего — конфликт: ничего не пишется, пока не `force`. Режим `check` только сообщает расхождения (`cyberzavod sync --check` в проверках проекта). Перевод строк `\r\n` расхождением не считается. **Манифест** `.cyberzavod/generated.json` (`manifest.ts`, `schemaVersion: 1`, в git): хеш sha256 каждого записанного файла (перевод строк приводится к `\n`) и запреты, которые адаптер сам дописал в настройки. Владение файлом (`ownershipOf`): нет файла — `missing`; хеш совпал с манифестом — `generated`; в манифесте, но хеш другой — `edited` (исправлен руками: не перезаписывается и не удаляется без `force`); не в манифесте, но с отметкой — `generated` (проекты до манифеста); остальное — `human`. Отчёт `SyncReport` — `added`, `updated`, `removed`, `conflicts` (файлы человека), `edited`. `previewClaude` строит тот же план для конфига, которого ещё нет на диске (`init` до записи), `requireWritable` бросает `fileConflicts`, если план упирается в чужие файлы. Сгенерированные тексты зовут CLI той версии, что в конфиге: `pinnedCliCommand(harness)` из `cli-command.ts` (`npx cyberzavod@<версия>`); подсказки человеку в сообщениях — `CLI_COMMAND` (`npx cyberzavod`).
- `disconnect.ts` — `disconnectClaude({ projectDirectory, check })`: удаляет нетронутые сгенерированные файлы и манифест (и опустевшие каталоги внутри `.claude/`), оставляет исправленные руками, из настроек убирает свои хуки и только те запреты, что записаны в манифесте; пустые настройки удаляются. С `check` только возвращает план.

## Сообщения (`src/messages/`)

Тексты адаптера для человека и агента — в каталогах `en.ts` и `ru.ts` (тип `ClaudeMessages` в `claude-messages.ts`: только ошибки адаптера; `CLAUDE_MESSAGES` в `catalog.ts`, экспортируется из `index.ts`). Тексты черновика и публикации, названия видов утечек `leakKinds` и полей шапки `headerFields` — в `KitMessages` кита. Язык выбирает CLI и передаёт готовый набор кита: в `HookContext.messages`, `DraftSessionOptions.messages`, `PublishSessionsOptions.messages` и параметром функций, которые печатают. Ошибка для человека — `ClaudeError` (`errors.ts`): она хранит `LocalizedText<ClaudeMessages>`, а не строку (`new ClaudeError((messages) => messages.errors.…)`), `message` всегда английский, текст на языке печати берёт `describe`; `GenerateError` — её наследник для генератора. Не переводятся: диагностика формата (`DraftError` из `parseDraft`, `RawLogError`, `SettingsError`, `RecordHookError`) — она на английском, содержимое записи (`VERDICTS`, причины `stage_fail`). Тексты генерируемых файлов (`generate/files.ts`, `statusMessage` в `generate/settings.ts`) и шаблонов — всегда английские, как harness; причины `stage_fail` — английские константы. `leaks.ts` и `unfilledHeader` отдают идентификаторы (`LeakKind`, `HeaderField`), а не подписи: подписи ставит тот, кто печатает.

## Хуки (`src/hooks/`)

Хуки — функции `HookContext → HookOutcome` (код выхода, stdout, stderr), их по имени вызывает `cyberzavod hook <имя>` (таблица `HOOKS` в `hooks/index.ts`). Сами хуки общие с другими агентами и лежат в `packages/adapter-kit/src/hooks/` (состояние между вызовами, `record`, `turn-start`, `stop` с тремя отказами и отметкой `human-call`, отпечаток кода, проверки; их тексты — `KitMessages`, тесты — там же), здесь только привязка к Claude: `record` получает источник событий `{ agent: "claude", eventOf: fromHookPayload }`. Каталог проекта хуку даёт `CLAUDE_PROJECT_DIR` (CLI).

## Запись сессии

Хук Claude Code → сырой журнал → черновик → редактура промптов и реплик → запись сессии ядра (по записи на каждую задачу сессии). Черновик и публикация — общий код кита (`packages/adapter-kit/src/capture/` и `src/commands/`, там же их тесты); описанное ниже про `to-draft.ts`, `draft.ts`, `builds.ts`, `leaks.ts` и команды относится к нему и одинаково для всех агентов. У Claude свои `capture/transcript.ts` (разбор транскрипта Claude Code), `capture/transcripts.ts` (`claudeTranscripts` — формат, отданный `transcriptsOf` кита) и тонкие `commands/draft.ts`, `commands/publish.ts`: они зовут общие команды с агентом `claude`, этими транскриптами и источником `{ type: "agent", provider: "anthropic", agent: "claude" }`.

- `hook-payload.ts` (`fromHookPayload`; модель события, `parseRawLog`, `isHumanPrompt` — в ките) — из полезной нагрузки хука берётся только нужное для записи. Содержимое файлов и ответы инструментов в журнал не попадают. У события `tool` — `cwd` вызова и `agentId`, если инструмент вызвал сабагент: по `agentId` вызов сабагента отличается от вызова основной сессии, по `cwd` находится проект команды. Из ответа сабагента — только первая строка: у станций `/feature` это вердикт. В десктопном приложении ответа в SubagentStop нет, и вердикт берётся из отчёта, который приходит в сессию сообщением (`UserPromptSubmit` → событие `subagent_report`). **Слова человека, кроме промпта.** Ответ на `AskUserQuestion` (`PostToolUse`) пишется событием `question_answer` с текстом «вопрос — ответ» по строке на вопрос: ответы берутся из `tool_response.answers`, а если их там нет — из `tool_input.answers` (в документации хуков `answers` описан только во входе, формат ответа не закреплён, разбор терпимый); без ответов остаётся обычный `tool`. Это текст человека, его можно писать, как текст промпта, а прочие ответы инструментов в журнал по-прежнему не идут. Промпт человека может нести `afterStopGate: true` — отметку, что перед ним хук остановки сдался и позвал человека (`markAfterStopGate` в ките): хук `record` на промпте человека (не на служебном сообщении) пробует удалить файл отметки (`claimHumanCallMarker` в ките), и если удалил, помечает промпт; нет файла — промпт как есть, другая ошибка — предупреждение, хук не падает.
- `to-draft.ts` — черновик из журнала. Этапы выводятся из действий агента по таблицам `TOOL_STAGES`, `COMMAND_STAGES` и `AGENT_STAGES`; возвраты станций `/feature` — по таблице `VERDICTS`, она по агенту (`tester`: `CHECKS PASSED`, `DONE`, `DEFECT`; `reviewer`: `APPROVED`, `NEEDS WORK`; русские вердикты harness до 0.8.0 из старых сырых журналов тоже остаются): чужое слово и первая строка агента без таблицы (`coder`, `analyst`) вердиктом не считаются. Новый признак этапа — новая строка в таблице, а не новое условие. **Место и проект команды.** Каталог вызова выводится из `cwd`, последнего `cd` перед командой в цепочке (`ToolPlace`: каталог, каталог сессии у старого журнала без `cwd`, неизвестно), `git -C` (только своей команде) и пути правимого файла. «Неизвестно» дают `~`, `$`, подстановки, `cd -`, `cd` без аргумента, подоболочка `(`, `pushd`, кавычки и обратная косая внутри пути и сегменты, начатые словом составной команды (`{`, `then`, `do`, `else`) или `command cd` (`{ cd /b; }`, `if …; then cd /b; fi`, `command cd /b`); другие `command` (`command -v jq`) место не меняют; тело heredoc в команды не разбирается, `<<` в кавычках heredoc не начинает, кроме двойных кавычек с незакрытой на этой строке `$(` или с `$(`, где внутри есть скобки или двойные кавычки (`"$(cat <<'EOF'`): там это настоящий heredoc, как у коммита с сообщением в heredoc. **Вызов из каталога вне проектов.** Если карта `projectsByDirectory` передана, а каталог вызова в ней нет (это не проект Cyberzavod: другой путь, dev-контейнер, нет или битый `.cyberzavod/project.json`), этап вызова в черновик не попадает, в том числе `draft_check`, от которого зависит исход сборки; каталоги с неизвестным местом и вызовы без карты этап сохраняют. Какие каталоги отброшены, возвращает `directoriesOutsideProjects`, о них предупреждает `draft.ts`. Проект каталога берёт из карты `DraftMeta.projectsByDirectory`, её собирает точка входа по `toolDirectories`; события основной сессии (`stage_enter`, `draft_check`, `stage_fail` без `run`) получают пометку `project`, если проект известен, а этап по инструментам не повторяется внутри проекта, пока станция не сбросит его. **Кто вызвал инструмент:** вызов с `agentId` открытой станции пропускается (внутри ревью запуск проверок — часть ревью); вызов без `agentId`, но с `cwd` — основная сессия, он записывается, если его каталог принадлежит проекту (см. выше); в старом журнале без обоих полей пропускается всё, пока открыто окно станции: отличить вызовы там нечем. Каждый старт станции даёт `stage_enter` с `run` и окно `draft_run` (до остановки, а без неё — до конца журнала), каждый вердикт станции и запуск проверок в основной сессии — `draft_check`.
- `draft.ts` — черновик: промпт в нём — событие `draft_prompt` с исходным текстом `said` и чистовой версией `goal` и `requirements`, вмешательство — `draft_intervention` с `reason` (ставит сборка черновика, редактор её не меняет), `said`, `line`, `text` и необязательным `build`, реплика — `draft_message` с `source` (`assignment`, `report` или `answer` — подсказка редактору, на сайт не идёт), `said`, `line` и `text`. У промпта, который сводится к «да» или «продолжай», редактор ставит `joined: true`: смысл уходит в предыдущий промпт, а на сайт склеенный не попадает. Пересобранный черновик забирает редактуру (сборки, промпты, `joined`, реплики, вмешательства) из прошлого; публикация превращает `draft_intervention` в `intervention` ядра без `said` (`line` и `text` проходят проверку на утечки, пустая `line` — ошибка) и убирает служебное (`said`, `source`, `run`, `project`, `build`, `draft_run`, `draft_check`, склеенные промпты) и собирает запись сессии ядра (`source` — `anthropic`/`claude`) и пропускает её через `parseRecord`.
- **Сборки в черновике.** Одна сессия может нести несколько задач, в том числе параллельных и в разных проектах, и публикуется несколькими записями. `Draft.builds` — список сборок `{ id, project, harness, workflow, title, language, runs, task? }`; `cyberzavod draft` создаёт одну, `builds[0]` с `id` черновика и проектом из `session_start`, остальные добавляет редактор (см. скилл). Необязательная `task` — метка задачи для сравнения прогонов на сайте: её ставит редактор только по слову человека, публикация кладёт её в `data.task`. `id` сборки — имя записи и файла, `parseDraft` отклоняет повторы, запуск в двух сборках и ссылку на неизвестную сборку.
- `builds.ts` — какие события к какой сборке и сколько длится сборка. Сборка — набор событий, а не отрезок времени: задачи идут вперемешку, а промпт человека задачу не отмечает. `eventBuilds`: запуск станции (`agentId`) относится к сборке, в чьём списке `runs` он указан, а запуск, не указанный нигде, — к первой; промпт человека, вмешательство и реплика — к сборке из поля `build` (так редактор отмечает промпт, с которого начинается задача); событие основной сессии с пометкой `project` — к сборке этого проекта: из нескольких к той, к которой относилось ближайшее предыдущее событие, а пока таких не было — к первой по порядку `builds` (у проекта без сборок правило не действует; такое событие текущую сборку не меняет, ответ человеку остаётся в задаче своего промпта); остальные события основной сессии — к сборке ближайшего предыдущего события с определённой сборкой, до первого такого — к первой. Проект ищется в `.cyberzavod/project.json` выше по каталогу, а не в хуке, поэтому находится и для старых журналов. Автоматически угадывать задачу по `#N` не нужно: номера issue повторяются между проектами. **Паузы:** промежуток, в котором у сборки не работает ни одна станция (окна `draft_run`) и нет её событий, сжимается до `IDLE_GAP_MS`; время отсчитывается от первого события сборки, а долгая работа станции без событий внутри не сжимается. Токены, начало и конец черновика в расчёт времени не входят.
- **Токены по сборкам.** Токены станции — её транскрипт по `agentId` (`DraftMeta.runTokens`): по `usage` с `run` на каждую модель запуска на последней остановке. Токены основной сессии берутся по сообщениям (`tokenUsages`, `DraftMeta.sessionUsages`) и ложатся `usage` по моделям на участок между соседними событиями с `run` или промптами человека, поэтому достаются той же сборке, что и участок. Публикация `usage` не складывает: они остаются в записи на своих местах с `model` и `breakdown`; сумма `tokens` по сборкам равна токенам журнала.
- **Итог сборки.** `build_start` и `build_end` в черновик не пишутся: публикация ставит `build_start` в 0, а `build_end.ok` берёт из последнего `draft_check` сборки (вердикт станции или запуск проверок в основной сессии), а без проверок — `true`. Провал соседней сборки на неё не влияет.
- **Публикация.** `cyberzavod publish [--draft …] [--build <id>]`. Без `--build` публикуются все сборки, и если хоть одна не готова, не пишется ничего; с `--build` — только она, незаконченные задачи из той же сессии можно опубликовать позже. Запись каждой сборки ложится в журнал проекта через `DirectoryRecordStore`: `sessions/<id сборки>.json`.
- **Проект сессии.** Хук `record` (в ките) находит проект по `CLAUDE_PROJECT_DIR` (вверх до `.cyberzavod/project.json`) и при `SessionStart` кладёт в `session_start` его `projectId`, `harness` и `workflow` (`stampProject`); без маркера сессия не пишется вовсе, битый конфиг — предупреждение, хук не падает. `toDraft` берёт их из первого `session_start`, где есть все три; `carryOverEdits` переносит заполненные редактором так же, как `title` и `language` (язык записи заполняет только редактор; черновик без поля читается с пустым), а пустые не публикуются (`unfilledHeader` называет, что ещё пусто).
- `leaks.ts` — страховка публикации: адреса, ключи и личные пути в тексте для сайта. Новый признак — новая строка в таблице.
- `transcript.ts` — токены, модели и тексты из транскрипта: токены сообщения делятся на виды (`input_tokens`, `output_tokens`, `cache_read_input_tokens` и запись в кэш; запись по времени жизни — из `cache_creation.ephemeral_5m_input_tokens` и `ephemeral_1h_input_tokens`, а часть `cache_creation_input_tokens`, которой нет в `cache_creation` (или весь он без `cache_creation`), считается пятиминутной; количество, не являющееся целым неотрицательным, считается нулём), модель — `message.model` того же сообщения (служебная `<synthetic>` — без модели), у повторов одного id берётся последний вариант; чтение кэша пишется в разбивку, но в счётчик `tokens` не входит; по первому ответу после промпта видно, какая модель его получила; из транскрипта сессии берутся ответы модели и задания сабагентам (`Agent`, `SendMessage`; у задания новому запуску есть `agentId` из результата вызова), из транскриптов станций — их отчёты (`SubagentHandback` или последний текст запуска). Формат транскрипта внутренний, разбор терпимый.
- Реплики в `to-draft.ts`: всё, что прозвучало в сессии, — ремарки трёх видов (`Remark`): `assignment` (задание станции), `report` (отчёт станции) и `answer` (итоговый ответ человеку — последний текст модели в ходе). Реплики получают `run` (запуск станции, о котором речь). Маршруты расставляет `routeMessages`, он вызывается в конце `toDraft` и снова после разметки сборок (`cyberzavod draft` делает это сам): он идёт отдельно внутри каждой сборки, поэтому отчёт станции одной задачи не адресуется станции другой. Ремарки сборки делятся на ходы (от её промпта или вмешательства человека до следующего, кроме ответа на вопрос модели: вопрос задан внутри хода и ход не начинает, как и в `turnsOf` для итоговых ответов; до первого промпта — свой ход), а `routeOf` даёт каждой маршрут исчерпывающим `switch` по виду. Задание станции X говорит X тому, кто сдал работу последним (отчёт другой станции раньше в ходе), а если такого нет — мастеру. Отчёт станции X говорит X тому, чьё задание идёт следом (другая станция), а если раньше ответ человеку или ход кончился — мастеру. Ответ говорит рабочий этапа в момент ответа мастеру. Так при передаче говорят оба: сдающий («Держи») и принимающий («Принял»). Агенты не из `AGENT_STAGES` (Explore, general-purpose) реплик не дают.
- **Вмешательства человека** в `to-draft.ts`: слово человека, которого ждала автоматика, — событие `draft_intervention` вместо `draft_prompt` (речь не задваивается). Причины (`InterventionReason` ядра): `question` — `question_answer`; `stop_gate` — промпт с `afterStopGate`; `plan_review` — первый промпт человека после `stop` основной сессии, если последний завершившийся запуск станции — `analyst` (таблица `AGENT_HUMAN_CALLS`: новая станция, после которой ведущий ждёт человека, — новая строка), а после него ни одна станция не стартовала; `rework_limit` — то же, но последний вердикт станции был возвратом (`judge` не пропустил). Состояние цикла: `pendingCall` ставят остановка станции и её вердикт, `awaitingHuman` берёт его на `stop`, старт станции сбрасывает оба, промпт человека забирает оба; служебное сообщение их не трогает. Если подходят несколько причин, `afterStopGate` главнее причины по станции.
- `commands/draft.ts` и `commands/publish.ts` — `draftSession` и `publishSessions`, их вызывает CLI (`cyberzavod draft` и `cyberzavod publish`). Вся логика — в чистых функциях с тестами. `draftSession` ищет проект каждого каталога из `toolDirectories` (`findProjectId` в `paths.ts` кита: вверх до первого `.cyberzavod/project.json`, битый конфиг — предупреждение) и собирает черновик по порядку `toDraft` → перенос редактуры → `routeMessages` и печатает число промптов, реплик и вмешательств и по каждой сборке проект, версию harness, процесс, число запусков и событий и что не заполнено, затем проекты, чьи команды есть, а сборки нет (`projectsWithoutBuild`: их команды достанутся сборке по времени), запуски станций без сборки (агент, `agentId`, время, первая строка задания) и предупреждения: каталоги вне проектов, чьи этапы и проверки не попали в черновик (`directoriesOutsideProjects`), запуск из `runs`, которого нет в журнале (`orphanedRuns`), и реплика с готовой строкой, у которой после пересчёта поменялся маршрут (`reroutedMessages`).

Рабочие файлы адаптера лежат в журнале проекта (`journal` конфига): сырые журналы — `capture/claude/raw/<сессия>.jsonl`, черновики — `capture/claude/drafts/<id>.json` (`captureDirectories` в `paths.ts` кита); в git они не идут. Журнал может лежать в репозитории проекта или рядом с ним (`../<проект>.cyberzavod`) — код один, отличается только путь.

Исходный текст промптов, вмешательств и реплик живёт только в журнале, транскриптах и черновике, всё вне git. Правила чистовой версии — в общем куске `recording-rules.md` кита, который подставляется в шаблон скилла `templates/publish-recording.md` (в проекте — `.claude/skills/publish-recording/SKILL.md`); реплики и вмешательства заполняет агент `recording-editor`. После публикации шаблон по согласию человека (`AskUserQuestion`) ведёт запись в галерею командами CLI `login`, `share`, `unshare` и `gallery --public`; запрос на удаление записи при лимите — обычное сообщение, потому что вариантов больше четырёх.
