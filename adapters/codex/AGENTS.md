# Адаптер Codex CLI (adapters/codex)

Второй адаптер агента. Собирает из harness и конфига проекта файлы, которые понимает Codex CLI, и держит доверие к проекту и его хукам в конфиге человека. Общая часть (владение файлами, манифест, формат файла хуков, шаблоны) — в `packages/adapter-kit`. Захват сессии, хук остановки и защита `.env` (`src/hooks/`, `src/capture/`), черновик и публикация записи сессии (`src/commands/`, разбор rollout'ов) работают. CLI о Codex знает только через `AgentAdapter` в `packages/cli/src/agents/codex.ts`. Живой `codex exec` против мока API проверяет e2e (`e2e/`, см. ниже).

## Генератор (`src/generate/`)

- `codex.ts` — что адаптер знает о Codex: ведёт только `openai`/`codex` (другой агент этапа — `CodexGenerateError`, наследник `CodexError`), модель по умолчанию по этапу (постановка и ревью — старшая, код и проверки — рабочая), `effort` этапа, модель второй доработки (`ESCALATION_MODEL`), модель редактора записи. Идентификаторы моделей — константы с комментарием «почему».
- `files.ts` — чистые тексты проектных файлов Codex: `.codex/config.toml` (`project_doc_max_bytes` — Codex иначе молча режет AGENTS.md на 32 КиБ — и `developer_instructions` с рабочими правилами), роль `.codex/agents/<роль>.toml` на каждый этап с ролью (Codex подменяет `developer_instructions` родителя ролевыми, поэтому в каждой роли рабочие правила и затем текст этапа), скиллы `.agents/skills/feature/` (таблица этапов, правила ведущего, как звать этап через `spawn_agent`: `agent_type` роли, задание в `message`, `fork_turns: "none"` — этап стартует с задания, а не с истории ведущего, и форк не принимает другую модель — и `task_name`, если инструмент его требует) и `.agents/skills/setup/` (из `templates/setup.md`), скилл `.agents/skills/publish-recording/` (из `templates/publish-recording.md` с общими кусками записи кита: `{{recordingRules}}`, термины `RECORDING_TERMS` — `$feature`, путь скилла и слова человека для вмешательств), роль `.codex/agents/recording-editor.toml` (модель `RECORDING_EDITOR_MODEL`, `model_reasoning_effort` `RECORDING_EDITOR_EFFORT`; `developer_instructions` — общий кусок `recording-editor.md` кита, собранный в коде, потому что роль — TOML, а не шаблон) и `agents/openai.yaml` рядом с каждым скиллом — `allow_implicit_invocation: false`: скиллы вызывает человек (`$feature`, `$setup`, `$publish-recording`). Скилл записи зовёт редактора через `spawn_agent` с `agent_type: "recording-editor"`, вопросы человеку задаёт обычным сообщением (`AskUserQuestion` у Codex нет), а вход в галерею ведёт через `exec_command` с короткой паузой `yield_time_ms` и опрос `write_stdin`, пока не появится `signed in:`. Песочница Codex по умолчанию пишет только в рабочий каталог и без сети, поэтому `login`, `share`, `unshare` и `gallery` скилл гоняет с `sandbox_permissions: "require_escalated"` и коротким `justification` (человек одобряет вызов); `draft` и `publish` — так же, если журнал вне репозитория. Отказ песочницы — не «другая ошибка»; не одобрено — остановиться и назвать команды для ручного запуска. `AGENTS.md` Codex читает сам, поэтому вложенных файлов рядом с ним нет.
- `toml.ts` — запись строк TOML (`tomlString`, `tomlMultilineString`) для генерируемых файлов.
- `hooks-config.ts` — хуки адаптера в `.codex/hooks.json`: запись на каждом событии (`record`, асинхронная; на `Stop` синхронная, потому что `codex exec` обрывает асинхронные хуки при выходе), `turn-start`, `guard` на `PreToolUse` для `Bash|apply_patch` (защита `.env`) и `stop`. Команда: `sh -c 'npx -y --prefer-offline --fetch-retries=0 --prefix "$(git rev-parse --show-toplevel 2>/dev/null || pwd)" cyberzavod@<версия> hook <имя> --agent codex || <запасной путь>'` (`inPosixShell` кита: Codex отдаёт команду логин-оболочке человека, а fish до 3.4 и tcsh не понимают `$(…)` и `||`; одинарные кавычки внутри команды — `'\''`). Codex запускает хук как `$SHELL -lc <команда>` в каталоге сессии и не даёт переменной с каталогом проекта; `--prefix .` в подкаталоге проекта не нашёл бы пакет в `node_modules` корня, поэтому префикс — корень git (проект подключают в корне репозитория, как и ищет Codex). Вне git — каталог сессии. Проект в подкаталоге большего репозитория пакет в своём `node_modules` по этому префиксу не найдёт: npx возьмёт его из кэша npm. Текст команды входит в хеш доверия: смена команды при `sync` переносит одобрение по паре (событие, имя хука), так что человеку ничего заново одобрять не нужно. События `PostToolUseFailure` у Codex нет.
- `sync.ts`, `inspect.ts`, `disconnect.ts` — как у Claude, поверх кита: `syncCodex`, `previewCodex` (`init` до записи), `inspectCodexHooks` (читает `.codex/hooks.json`, ничего не пишет), `disconnectCodex`. Файл хуков делят адаптер и человек: свои обработчики заменяются, чужие остаются. Файлов, которых больше нет в плане, не удаляет без отметки или записи в манифесте.

## Черновик и публикация (`src/capture/rollout.ts`, `transcripts.ts`, `src/commands/`)

Сами `draft` и `publish` общие (`draftSession`, `publishSessions` кита, см. его AGENTS.md); Codex даёт им формат транскрипта, агента `codex` и источник записей `CODEX_SOURCE` — `{ type: "agent", provider: "openai", agent: "codex" }`. `commands/draft.ts` и `commands/publish.ts` — тонкие обёртки, CLI зовёт их через `agents/codex.ts`. Сырой журнал сессии — `capture/codex/raw/<сессия>.jsonl`, черновики — `capture/codex/drafts/`.

- **Rollout** — JSONL сессии (`transcriptPath` из `Stop` и `SubagentStop`): строки `{timestamp, type, payload}`. Формат внутренний, разбор терпимый: непонятные строки пропускаются. `rollout.ts` читает: модель по ходам (`turn_context.model`), тексты ответов (`response_item` с ролью `assistant`; у прежней «legacy» истории, где `response_item` нет, — события `agent_message`), токены, задания сабагентам, отчёты сабагентов и исходы команд. Фикстуры (`rollout.fixtures.ts`) — живой прогон Codex 0.162.1 с путями `/project` и `/codex-home` и построенные по источникам Codex (помечены «Documented»).
- **Модель промпта.** `turn_context` пишется до сообщения человека и раньше хука промпта, поэтому ответ модели датируется последней строкой своего хода (`rolloutModelReplies`): первый ответ, закончившийся после промпта, — тот, что на него ответил.
- **Токены** (константы и правило — в `rollout.ts`): на каждый ответ модели (`token_usage_record`, один `response_id` считается один раз; форк потока (`fork_context`) копирует записи родителя, поэтому считаются только записи с `thread_id` этого rollout'а — `session_meta.id`, а запись без `thread_id` своя) — входные без кэша плюс выходные; чтение из кэша не считается, как у Claude. Токены сабагента — его rollout по `transcriptPath` остановки, токены сессии делятся на сборки по ответам.
- **Задания и отчёты.** Задание — вызов `spawn_agent` (`message`, `agent_type`) в любом пространстве имён инструментов или `send_input`/`followup_task` (`target`, `message`). Сабагента вызов называет двумя способами. V1 (`multi_agent_v1`): `agent_id` в результате вызова `{"agent_id", "nickname"}` — он равен `agent_id` хуков и `session_meta.id` rollout'а сабагента. V2 (`collaboration`, модель по умолчанию): результат — только `{"task_name": "/root/<имя>"}`, а `agent_id` лежит в `item_completed` с `SubAgentActivity` вида `started` (`id` — id вызова, `agent_thread_id`, `agent_path`); `rollout.ts` связывает их по id вызова, а `send_input`/`followup_task` с целью-путём приводит к id потока. Задание подагента V2 приходит в его rollout как `agent_message`. Отчёт — `last_agent_message` строки `task_complete` rollout'а сабагента, а у запуска, который оборвали, — последний текст модели; только по собственным ходам (`turn_id` записей с `thread_id` этого rollout'а), ходы родителя из форка пропускаются. Запуск без текста отчёта не даёт.
- **Исход команд.** Хук Codex пишет каждый вызов `Bash`/`apply_patch` как `ok: true` (`PostToolUseFailure` нет), поэтому черновик исправляет `ok` по rollout'у (`toolOutcomes` в `TranscriptFormat`, связь по `callId`): `item_completed` с `CommandExecution` (`status`, `exit_code`) главнее, затем строка `Process exited with code N` или `Exit code: N` в шапке ответа инструмента (до строки `Output:`: вывод самой команды кода выхода не даёт). Команда, которая ещё шла, исхода не имеет, остаётся `ok: true`.
- **Сжатые rollout'ы.** Codex может хранить старый rollout как `<файл>.zst`; `readRollout` (`transcripts.ts`) отвечает `compressed`, если простого файла нет, а сжатый есть, и черновик предупреждает, что токены и тексты оттуда не вошли; ошибка поиска сжатого файла, кроме «нет файла», — `failed` с причиной. Распаковки нет.
- `apply_patch` в `TOOL_STAGES` кита — этап «реализация», как `Edit`/`Write` у Claude.

## Доверие (`src/trust/`)

Codex запускает хуки проекта, только если конфиг **человека** (`$CODEX_HOME/config.toml` или `~/.codex/config.toml`, `codex-home.ts`) доверяет проекту (`[projects."<realpath>"] trust_level = "trusted"`) и хранит хеш каждого хука (`[hooks.state."<hooks.json>:<событие>:<группа>:<обработчик>"] trusted_hash = "sha256:…"`). Хеш — sha256 компактного JSON с отсортированными ключами из `event_name`, `matcher` (кроме `UserPromptSubmit`, `Stop`, `Interrupt`) и обработчика с нормализованным таймаутом (`hook-trust.ts`; эталонные хеши в тесте посчитаны независимо). Без доверия Codex молча не видит роли и не запускает хуки.

- Файл человека правится **построчно** (`toml-lines.ts`, `config-toml.ts`): комментарии, порядок и перевод строк сохраняются, дописывается и убирается только своё. Строка доверия проекту несёт `TRUST_MARK` (`# added by cyberzavod`): по ней `disconnect` отличает своё от доверия, которое дал человек. Если строка заменила другое значение (например `untrusted`), отметка его хранит (`# added by cyberzavod, was "untrusted"`), и `disconnect` возвращает его. Каждая правка проверяется разбором `smol-toml` (результат обязан отличаться от исходного ровно на запланированное — иначе `configEditRejected`); раскладка, которую построчно не поправить (инлайн-таблицы и подобное), и не-TOML — `CodexError` до записи.
- `trust.ts` — план, потом запись: `planConnectTrust`, `planDisconnectTrust` возвращают `TrustPlan` (`changes`, `keptProjectTrustFile`, `apply`) — ошибки конфига падают до первой записи. `carryOverTrust(источник, корень, действие)` для `sync` переносит одобрение по паре (событие, имя хука; имя — из команды `hook <имя>`, `HookTrust.name`): новый свой обработчик одобряется, только если прежний с тем же событием и именем был одобрен; одобрение, которое человек снял или не давал, не выдумывается, записи заменённых обработчиков снимаются. Нет прежних своих хуков — `config.toml` даже не читается. `sync` доверия не создаёт. `inspectTrust` ничего не пишет и отвечает `trusted`, `projectUntrusted`, `hooksUntrusted` или `unreadable` (не TOML в `config.toml`, не JSON или неверная форма `.codex/hooks.json` — группы разбирает проверяющий `groupsOf` кита). Запись атомарная (временный файл + `rename`, права сохраняются, символическая ссылка разыменовывается).
- Доверие пишет только `init` после своего единственного подтверждения; `sync --check` состояние машины не смотрит, его проверяет `doctor` (проверка `trust`). Тесты работают с временным `CODEX_HOME`, настоящий домашний каталог не трогается.

## Хуки (`src/hooks/`, `src/capture/`)

Хуки зовёт `cyberzavod hook <имя> --agent codex` (`CODEX_HOOK_NAMES`: `record`, `turn-start`, `stop`, `guard`; `runCodexHook` в `hooks/index.ts`). `record`, `turn-start` и `stop` — общие хуки кита (`recordEvent`, `startTurn`, `gateStop`: состояние, отпечаток кода, три отказа, отметка `human-call`), здесь к ним только привязка к Codex. Отличия от Claude:

- **Каталог проекта.** У хука Codex нет `CLAUDE_PROJECT_DIR`: CLI берёт `cwd` из нагрузки, а `runCodexHook` поднимается от него до маркера проекта (`findProjectRoot`), потому что проверки и отпечаток кода работают от корня, а сессия может идти в подкаталоге.
- **Нагрузки** (`capture/hook-payload.ts`, `fromCodexHookPayload`): `SessionStart` → `session_start`; `UserPromptSubmit` → `prompt`, но с `agent_id` (задание, которое получил сабагент) — ничего; `PostToolUse` → `tool`: у `Bash` (`SHELL_TOOL`, имена инструментов — в `generate/codex.ts`) команда (до 200 знаков) и `callId` (`tool_use_id`, по нему черновик сверит исход с транскриптом), у `apply_patch` первый файл патча абсолютным путём (`patch-paths.ts`) без текста патча, у прочих инструментов только имя; `cwd` и `agentId` — у всех; ответ инструмента не пишется никогда; `SubagentStart`/`SubagentStop` → `subagent_start`/`subagent_stop` (`transcriptPath` — `agent_transcript_path` или `transcript_path`, вердикт — первая строка `last_assistant_message`); `Stop` → `stop` с `transcriptPath`. Остальное (`PreToolUse`, `SessionEnd`, …) в журнал не идёт. События `PostToolUseFailure` у Codex нет, поэтому каждый записанный вызов — `ok: true`; исход команды черновик берёт из rollout'а (см. «Черновик и публикация»). Фикстуры (`hook-payload.fixtures.ts`) — живые нагрузки Codex 0.162.1 с путями `/project` и `/codex-home`; нагрузки, которых живой прогон не дал (`SubagentStop`, `Bash` и `apply_patch` в `PostToolUse`, `wait_agent`), собраны по схеме и документации Codex и помечены «Documented».
- **`SubagentStart`** несёт `transcript_path` rollout'а сабагента: он записывается в `subagent_start` (`transcriptPath`), и черновик берёт токены и отчёт оборванного запуска (без `SubagentStop`) из него.
- **`turn-start`** пропускает вызов с `agent_id`: промпт сабагента — его задание, ход принадлежит основной сессии.
- **Запись на `Stop` синхронная** (в `hooks-config.ts`): `codex exec` обрывает асинхронные хуки при выходе, и последнее событие сессии пропало бы.
- **Служебные «сообщения пользователя»** Codex (`<hook_prompt …>` — причина отказа хука остановки, `<turn_aborted>`) не слова человека: они в `SERVICE_MESSAGE_PREFIXES` кита, так что не забирают отметку `human-call` и не становятся промптами.
- **`guard`** (`hooks/guard.ts`) — `PreToolUse` для `Bash|apply_patch`. `Bash`: слова команды (без кавычек, операторов, подстановок и `=`), у которых имя файла — `.env`, начинается с `.env.` (как `**/.env` и `**/.env.*` у Claude) или с `.env` и знака маски (`.env*`, `.env?`, `.env[.]local`: оболочка раскроет её до открытия файла); `.envrc` и `env.ts` проходят. Маска, прячущая начало имени (`.en?`, `.[e]nv`), не ловится: отличить её от других имён можно только по файловой системе. `apply_patch`: пути из заголовков патча по тому же правилу, а также пути внутри `<журнал>/capture/codex/raw/` (журнал из конфига; битый конфиг оставляет только правило `.env`). Отказ — JSON `permissionDecision: "deny"` с причиной из `CodexMessages.guard` и кодом 0. Это сопоставление строк, не разбор оболочки: имя файла, собранное из кусков, проходит; правка сырых журналов через `Bash` не закрыта. Запасной путь у `guard` — `true` (без сети npx защита молча пропускает, иначе Codex без сети был бы непригоден).
- `systemMessage` хука остановки (отпуск с сообщением) — общее поле вывода хуков Codex. `codex exec` печатает в stderr только `hook: Stop Completed`, текст предупреждения он не показывает, поэтому e2e проверяет принятие вывода (статус `Completed`, а не `Failed`) и отпуск после трёх отказов; сам текст видит человек в интерактивном Codex, живьём его не подтвердить.

## Сообщения (`src/messages/`)

`CodexMessages` в `codex-messages.ts` (причины отказа `guard` и ошибки), каталоги `en.ts` и `ru.ts`, `CODEX_MESSAGES`. Тексты хуков остановки и записи общие — `KitMessages`. Ошибка — `CodexError` (`errors.ts`), как `ClaudeError`: хранит `LocalizedText<CodexMessages>`, `message` английский. Тексты генерируемых файлов и шаблонов — всегда английские.

## Проверка на живом Codex (`e2e/`)

`make check-codex` (`pnpm --filter @cyberzavod/adapter-codex e2e`, отдельный `vitest.e2e.config.ts`; обычный `vitest.config.ts` берёт только `src/**/*.test.ts`) гоняет настоящий `codex exec` против мока Responses API (`mock-responses.ts`: HTTP-сервер, SSE-ответы, сценарий решает по присланной истории, что «модель» делает дальше). Хуки, роли, подагенты, npx и проверка доверия настоящие, обхода доверия нет; поддельна только модель. В CI это задача `codex-e2e`.

- **Инструменты** (`workspace.ts`): собранный и установленный в проект пакет `cyberzavod`, Codex версии `CODEX_E2E_VERSION` (`codex-version.ts`; ставится `npm install @openai/codex@<версия>`, готовый бинарник — `CODEX_E2E_BIN`; прогон отказывается от любой другой версии), временный `CODEX_HOME` с конфигом, который направляет Codex на мок (`[features] plugins = false`, чтобы фоновая загрузка плагинов не писала в каталог при его удалении). Хуки Codex запускает через `$SHELL -lc`; подменный `SHELL` сохраняет `PATH` прогона. `INIT_CWD` из окружения убирается: pnpm выставляет его, а CLI берёт его за каталог проекта. `CODEX_E2E_KEEP=1` оставляет каталог прогона.
- **Сценарии** (`scenarios.ts`, `codex.e2e.test.ts`): процесс завода (ревьюер-подагент, отказ защиты на `cat .env`, один возврат на остановке при красной проверке, сырой журнал, черновик, публикация записи с источником `openai/codex`, отключение возвращает конфиг человека), сессия в подкаталоге проекта (журнал пишется в корень проекта; три отказа остановки, затем отпуск) и `draft` в песочнице Codex без сети. Один `codex exec` на сценарий делят несколько `it`.
- Версия Codex поднимается осознанно: нагрузки хуков, хеш доверия и смысл `block` — внутренности Codex.

## Правила

- Привязка к агенту — в `codex.ts` и в названиях каталогов/событий; всё, что общее с Claude, — в ките.
- `terms` адаптера (`Codex`, `$имя`) используются в текстах CLI, а не зашиты в них.
- Тесты — на временном каталоге; `smol-toml` нужен только этому пакету (CLI получает его в бандле, `dist/THIRD_PARTY_LICENSES`).
