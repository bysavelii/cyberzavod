# Киберзавод

Cyberzavod — локальный, независимый от модели harness разработки с ИИ-агентами: процесс (этапы, роли, принципы), конфиг проекта, генерация файлов агента и журнал сессий и решений. Этот репозиторий — сам Cyberzavod и его сайт cyberzavod.com: цех в браузере (вид сверху) проигрывает сессии, в которых агенты по процессу завода с нуля собирают проекты-примеры. Код открытый, сайт для портфолио.

Граница одна: инструмент — npm-пакет `cyberzavod` (`packages/cli` со всем, что он собирает в один файл: ядро, хранилище, адаптер, harness), его ставят в любой проект командой `npx cyberzavod init`, клон этого репозитория для этого не нужен. Сайт (с проигрывателем `packages/player`) и API — отдельное приложение, которое знает только формат записей журнала. Этот репозиторий подключён к инструменту так же, как любой другой проект, отличие одно: пакет `cyberzavod` здесь — workspace-пакет (devDependency корня), хуки находят его через npx в `node_modules`, а `prepare` в `packages/cli` собирает `dist/` при `pnpm install`.

Этот файл — правила проекта для агентов и людей. `CLAUDE.md` в корне и в частях генерирует `cyberzavod sync` поверх AGENTS.md — руками их не правят. Правила частей лежат рядом с кодом: `apps/web/AGENTS.md`, `apps/api/AGENTS.md`, `packages/core/AGENTS.md`, `packages/player/AGENTS.md`, `packages/storage/AGENTS.md`, `packages/adapter-kit/AGENTS.md`, `packages/cli/AGENTS.md`, `adapters/claude/AGENTS.md`, `adapters/codex/AGENTS.md`.

## Команды

- `make check` — все проверки: типы, тесты, сборка фронта и API, e2e Codex, сборка Docker-образа. CI вызывает те же make-цели. Должна проходить перед любым коммитом.
- `make check-web check-api` — проверки без Docker; их же запускает хук остановки (`verification.commands` в `.cyberzavod/project.json`). `check-web` заодно проверяет `cyberzavod sync --check`: сгенерированные файлы не отстали от harness и конфига.
- `pnpm smoke` — дымовая проверка настоящего npm-пакета: `npm pack`, установка архива и путь человека от `init` до `disconnect` во временном проекте, для Claude Code и для Codex; CI гоняет её на Linux, macOS и Windows.
- `make check-codex` — e2e адаптера Codex: настоящий `codex exec` (версия закреплена в `adapters/codex/e2e/codex-version.ts`) против мока API модели, без обхода доверия к хукам. Входит в `make check`, но не в `check-web check-api`: ставит Codex из npm (`CODEX_E2E_BIN=<путь>` берёт готовый). CI гоняет его задачей `codex-e2e`, образы без него не собираются.
- `make dev` — Postgres и API в Docker, фронт с горячей перезагрузкой на http://localhost:4321.
- `make up` / `make down` — поднять или остановить Docker-окружение.
- `make format` — привести код к стилю (Prettier, ESLint --fix, gofumpt, goimports).
- `pnpm cyberzavod <команда>` — собрать CLI из рабочей копии и запустить: `init`, `sync`, `doctor`, `status`, `disconnect`, `decision`, `note`, `draft`, `publish`, `hook`, `login`, `logout`, `share`, `unshare`, `gallery`; `pnpm cyberzavod --help` — команды по разделам, `pnpm cyberzavod <команда> --help` — флаги команды.
- `pnpm cyberzavod sync` — после правки `harness/`, шаблонов, CLI, адаптера или конфига: перегенерировать `CLAUDE.md` и `.claude/`. `make check-web` ловит, если забыли.
- `/feature <номер issue>` — провести задачу через процесс: постановка (ждёт одобрения человека), код, ревью, проверки, фиксация.
- `/publish-recording` — опубликовать сессию: черновик из сырого журнала, чистовая редактура промптов и реплик, проверка человеком, запись в `.cyberzavod/journal/sessions/`. Оттуда запись уходит на сайт, поэтому сессию самого завода публикуют только вместе с его карточкой (см. `projects/` в «Устройстве»). Затем по согласию человека скилл отправляет запись в его личную галерею: вход, ссылка, открытие галереи и бейдж.
- `make help` — остальные команды.

Если работаешь в dev-контейнере (`DEVCONTAINER=true`, см. `.devcontainer/README.md`): Docker и доступа к серверу там нет намеренно. Перед коммитом — `make check-web check-api`, проверки с Docker выполнит CI. API — `make api-dev`, сайт — `pnpm dev --host`.

## Устройство

Монорепозиторий: pnpm workspaces для TypeScript, отдельный Go-модуль для API. Зависимости направлены к ядру: адаптеры и CLI знают о ядре и хранилище, адаптеры — ещё об общей части `packages/adapter-kit`, ядро — ни о ком.

- `packages/core` — модель на чистом TypeScript: записи журнала (конверт `{version, type, timestamp, projectId, sessionId, source, data}`, типы `session`, `decision`, `note`), конфиг проекта, этапы и процесс, harness, счётчики.
- `packages/player` — проигрыватель цеха: сценарий из записи и кадр в любой момент. Только для сайта; в npm-пакет инструмента не входит.
- `packages/storage` — диск: чтение конфига проекта, `DirectoryRecordStore` (журнал как каталог файлов), загрузка harness. Одно хранилище для CLI, адаптера и сайта.
- `packages/cli` — npm-пакет `cyberzavod`: `init [--agent claude|codex]` с распознаванием проекта и одним подтверждением, `sync`, `doctor` (проверка подключения с подсказками, как починить), `status`, записи решений и заметок; сообщения на английском и русском; `draft` и `publish` передаёт адаптеру проекта, `hook` — адаптеру из флага `--agent` (по умолчанию `claude`); `login`, `share`, `unshare` и `gallery` — вход через GitHub и личная галерея записей на сайте (не больше 5 записей, по умолчанию закрыта). `scripts/build.ts` собирает всё в `dist/cyberzavod.mjs` без зависимостей.
- `packages/adapter-kit` — общая часть адаптеров агентов: владение сгенерированными файлами и манифест, план синхронизации и отключения, файл хуков, хуки записи, начала хода и остановки (их тексты и состояние), модель сырого журнала, черновик и публикация записи сессии (команды `draft` и `publish`, сборки, проверка утечек, чтение транскриптов — разбор формата даёт адаптер), шаблоны и тексты процесса и записи, общие сообщения. Ни одного агента по имени не знает.
- `adapters/claude` — адаптер Claude Code: генератор `CLAUDE.md`, агентов, скиллов и `.claude/settings.json`; хуки записи сессии и остановки; разбор транскриптов Claude Code для черновика, источник записей `anthropic`/`claude`; шаблоны того, что не выводится из harness.
- `adapters/codex` — адаптер Codex CLI: генератор `.codex/config.toml`, ролей `.codex/agents/*.toml`, скиллов `.agents/skills/` и `.codex/hooks.json`; доверие проекту и хукам в конфиге человека (`$CODEX_HOME/config.toml`), которое пишет `init` после подтверждения. Хуки Codex — запись сессии, начало хода, остановка и защита `.env` (`cyberzavod hook <имя> --agent codex`); черновик и публикация записи Codex (разбор rollout'ов, источник `openai`/`codex`), скилл `$publish-recording` и роль `recording-editor`; живой прогон — следующий этап задачи #87.
- `harness/` — процесс, который Cyberzavod даёт каждому проекту: принципы, этапы, процессы (`workflows/default.json`), правила ведущего. Тексты не называют проект, язык, модель и хостинг.
- `.cyberzavod/generated.json` — манифест сгенерированных файлов (хеши) и запретов адаптера: по нему `sync` и `disconnect` отличают свой файл от исправленного руками. Пишет `cyberzavod sync`.
- `.cyberzavod/project.json` — маркер и конфиг проекта: `schemaVersion`, `projectId`, версия harness, процесс, путь журнала, агент на каждый этап (`provider`, `agent`, `model`), команды проверок и каталоги кода для хука остановки.
- `.cyberzavod/journal/` — журнал в git: `sessions/`, `decisions/`, `notes/`. `capture/<агент>/` в нём (`capture/claude/`, `capture/codex/`) — сырые журналы и черновики адаптера, вне git. `sessions/` — записи сайта: сборки проектов-примеров, которые цех собрал с нуля; сайт берёт их при сборке.
- `projects/` — карточки проектов для сайта (название, описание, ссылки, стек), в git; сайт берёт их при сборке. У каждой записи в `.cyberzavod/journal/sessions/` должна быть карточка её `projectId`: запись без карточки роняет сборку. Сам завод — тоже проект (`projectId` `cyberzavod`), но его сборки сейчас на сайте не показываются: запись его сессии кладут в `sessions/` только вместе с карточкой `projects/cyberzavod.json`.
- `guides/` — гайды для сайта в Markdown, в git: `<id>.<язык>.md`, по файлу на каждый язык сайта; сайт берёт их при сборке; новый гайд — новые файлы.
- `apps/web` — сайт: Astro + SolidJS + Nano Stores, слои FSD, свой ui-kit на Kobalte, цех на весь экран на canvas через PixiJS.
- `apps/api` — API на Go с Postgres: галереи записей, бейдж для README, аналитика по открытым галереям.
- `compose.yaml` — локальное окружение: db → migrate → api.

Деплой автоматический: push в `main` → проверки → образы `ghcr.io/bysavelii/cyberzavod-{api,web}:<sha>` → CI вызывает по SSH выкатку этого sha и передаёт на stdin временный токен job'а для скачивания приватных образов. Сервер в этом репозитории не описан: проект знает только адрес, свой ключ и sha. На сервере перед переключением версии применяются миграции, поэтому миграции совместимы с предыдущей версией API: сначала добавляем, удаляем только следующим релизом.

Цех рисует только то, что выводится из событий записи через сценарий проигрывателя (`packages/player`). Новое визуальное состояние начинается с нового типа события в `packages/core`.

## Хуки Claude Code (`.claude/settings.json`)

Хуки записи и остановки, запреты на `.env` и сырые журналы кладёт и обновляет `cyberzavod sync`; остальное в файле — правила этого проекта, sync их не трогает.

- **Запись:** каждое событие сессии (промпт, вызов инструмента, сабагент, остановка) асинхронно дописывается в `.cyberzavod/journal/capture/claude/raw/<сессия>.jsonl`. Хуки — `npx -y --prefer-offline --fetch-retries=0 --prefix "$CLAUDE_PROJECT_DIR" cyberzavod@<версия harness из конфига> hook <имя> || <запасной путь>`: пакет берётся из кэша npm или из `node_modules` проекта (здесь — workspace-пакет, его собирает `pnpm install`), без сети npx падает сразу. Без npm запись и начало хода молча пропускаются, остановка отпускает агента с сообщением человеку. Начало сессии несёт проект, версию harness и процесс из `.cyberzavod/project.json`. Сырые журналы вне git; из ответов инструментов в журнал попадает только ответ человека на `AskUserQuestion`; в запись сессии попадают только этапы, счётчики, промпты, реплики и вмешательства человека в чистовом виде — после проверки человеком.
- **Остановка:** команды проверок и каталоги с кодом хук берёт из `verification` в `.cyberzavod/project.json`. Если агент в этом ходе менял код в этих каталогах, он не может закончить, пока команды красные; после трёх неудачных попыток подряд останавливается и зовёт человека. Отказ — JSON-решение `block` с кодом выхода 0, а не код 2: ненулевой код в команде хука значит «npx не запустился». Чужие незакоммиченные правки, сделанные до хода, агента не держат: в начале хода хук `turn-start` запоминает отпечаток кода. Подробности — в `adapters/claude/AGENTS.md`.
- **Облако:** в облачной сессии Claude Code (`CLAUDE_CODE_REMOTE=true`) `.claude/hooks/session-start.sh` на старте и при возобновлении ставит зависимости pnpm (заодно `pnpm install` собирает CLI для хуков; первый `SessionStart` приходит до установки, и его запись пропускается) и, если нужно, пересобирает golangci-lint: версия — из `GOLANGCI_LINT_VERSION` в `.devcontainer/Dockerfile`, Go — из `apps/api/go.mod`. Без этого образ облака не проходит `make check-web check-api`, и остановка не отпускает агента. Локально и в dev-контейнере хук ничего не делает.
- **Go:** после правки `.go`-файл форматируется `golangci-lint fmt` (gofumpt и goimports), как в `make check-api`.
- **Запреты:** инструментам чтения и правки закрыт `.env`, правке — сырые журналы (`permissions.deny`). Команды Bash эти правила не перекрывают: `.env` всё равно не читать.

## Harness и адаптер

- Тексты `harness/` — общие для любого проекта: не называют Киберзавод, его команды, каталоги, трекер и модели. Всё проектное — в AGENTS.md проекта и в `.cyberzavod/project.json`. Тексты harness, шаблонов адаптера и генератора — на английском: проект пользователя получает английский процесс при любом языке человека; правила самого проекта (AGENTS.md) пишут на языке команды, здесь — на русском.
- Версия harness — `HARNESS_VERSION` в `packages/cli/src/installation/installation.ts`, она же `version` npm-пакета; `sync` пишет её в конфиг проекта. Меняется вместе с правкой `harness/` или шаблонов адаптера.
- Выпуск в npm: поднять версию, затем тег `vX.Y.Z` — CI проверяет, что тег совпадает с версией пакета, гоняет дымовую проверку и публикует его (`.github/workflows/release.yml`, Trusted Publishing npm без токена). Шаги — в `RELEASING.md`.
- Сгенерированный файл несёт отметку `Generated by cyberzavod sync`: sync перезаписывает и удаляет только такие файлы; прежнюю русскую отметку `Сгенерировано cyberzavod sync` (версии до 0.8.0) он тоже узнаёт, так что подключённые проекты обновляются без `--force`. Чтобы поменять сгенерированный текст, правят harness, шаблон адаптера или генератор, затем `pnpm cyberzavod sync`.
- Новый агент — новый каталог `adapters/<агент>` со своим генератором и захватом сессии, новый член `AGENT_NAMES` и объект адаптера в `packages/cli/src/agents/`; ядро, хранилище, harness и общая часть `packages/adapter-kit` при этом не меняются, пока общего кода нет. Проект ведёт один агент (`init --agent <имя>`, по умолчанию `claude`).

## Модели и расход

- Агенты этапов — в `.claude/agents/`, их модель и effort выводит генератор из `agents` в `.cyberzavod/project.json`; `model: "default"` — выбор адаптера: постановка и ревью — Opus, код и проверки — Sonnet. Редактор реплик `recording-editor` (`/publish-recording`) — Sonnet на среднем effort. Повторная доработка переходит на Opus, после третьего возврата процесс зовёт человека. Возвраты этапов попадают в запись сессии, возвраты по CI и проверке сайта — нет.
- Сабагенты без своей модели, например general-purpose, работают на Sonnet (`CLAUDE_CODE_SUBAGENT_MODEL`). Встроенные Explore и Plan наследуют модель сессии. Effort проекта — `high`, контекст сжимается на 400 тыс. токенов (`.claude/settings.json`).
- Больше всего стоит длинный контекст, а не модель: каждый запрос заново читает всю историю. Одна задача — одна сессия; объёмную работу — агентам со свежим контекстом.

## Качество кода

Код должен читаться как описание того, что он делает, и расширяться добавлением, а не правкой по всему проекту. Конкретно:

- **Имена из предметной области.** Запись, сессия, этап, цех, возврат — а не `data`, `item`, `handle`, `process`. Без сокращений, кроме общепринятых (`ctx`, `err`, `id`).
- **Одна функция — одно действие.** Если функцию нельзя назвать без «и», её надо разделить. Тело читается сверху вниз без прыжков: сначала ранние выходы, потом основной путь.
- **Расширение через типы, а не через условия.** Новый вариант — новый член размеченного объединения (TS) или новая реализация интерфейса (Go). Ветвление по варианту — исчерпывающий `switch`, где пропущенный случай ловит компилятор, а не цепочка `if` по строкам в разных файлах.
- **Абстракция — когда появился второй реальный случай.** Не заводить интерфейс, фабрику или параметр «на будущее».
- **Зависимости направлены внутрь.** Ядро ничего не знает о сайте и API; бизнес-логика не знает о фреймворке, базе и HTTP — только об интерфейсах.
- **Ошибки не глотаются.** Либо обработать, либо вернуть с контекстом (`fmt.Errorf("загрузка миграций: %w", err)`, свой класс ошибки в TS).
- **Комментарий объясняет «почему»**, когда это не видно из кода. Пересказ кода словами, закомментированный и мёртвый код не допускаются.
- **Без магических значений.** Числа и строки со смыслом получают имя.

## Стиль кода

Проверяется инструментами: `make check` падает при нарушении, `make format` приводит код к стилю.

- **TypeScript:** Prettier (ширина 100, двойные кавычки, точки с запятой, запятые в конце списков) и ESLint (typescript-eslint strict и stylistic, Solid, Astro, JSDoc, Vitest).
- **Читаемость** (принцип `harness/principles/readability.md`): то, что проверяется автоматически, проверяет ESLint — пустые строки между блоками (`@stylistic/padding-line-between-statements`: после объявлений, вокруг многострочных блоков и `if`, перед `return`), вложенность блоков не глубже двух (`max-depth`), без вложенных тернарных операторов, `prefer-const`, без правки параметров (`no-param-reassign`). Имена промежуточных результатов и условий, один уровень абстракции и флаги-переключатели проверяет ревью.
- **JSDoc** — на всём экспортируемом: функции, компоненты, классы, типы, интерфейсы, константы. Одно-два предложения о том, что это и зачем, без описания реализации. У функций — `@param` на каждый параметр, `@returns`, и `@throws`, если функция бросает ошибку; у `@param` и `@returns` тип в фигурных скобках: `@param {number} ms Duration in milliseconds.` Тип в JSDoc должен совпадать с сигнатурой TypeScript — линтер проверяет только его наличие, совпадение проверяет ревьюер.
- **Go:** golangci-lint (staticcheck, errcheck, revive, gofumpt, goimports). Doc-комментарий — на каждом экспортируемом идентификаторе и на пакете; начинается с имени, дальше по-английски: `// Load reads the settings from the environment.` Неэкспортируемое — по желанию, когда имя не говорит само за себя.
- Комментарии внутри кода — только «почему».

## Тесты

- Новая логика — с тестом рядом.
- **TypeScript — Vitest.** Каждая группа тестов — в `describe` с именем проверяемой функции или компонента, внутри — `it` с поведением по-русски: `describe("parseRecording")` → `it("отклоняет неизвестный этап")`. Тест вне `describe` — ошибка линтера.
- **Go — стандартная библиотека.** `TestXxx` на проверяемую функцию, случаи — таблицей, каждый в `t.Run`; проверки через `if` и `t.Fatalf` с понятным сообщением.
- **Arrange / Act / Assert** — три блока, разделённые пустой строкой, без комментариев-меток. Если готовить нечего, блока Arrange нет.
- Act — одно действие над проверяемым кодом. Для исключения: `const act = () => parse(raw);`, затем `expect(act).toThrow(…)`.
- Тестовые данные собираются фабрикой (`validRecording()`), а не общей мутируемой переменной.
- Shell-тесты хуков и деплоя — по тем же правилам: функция на сценарий, блоки через пустую строку.

`make format` выполняет Prettier, затем ESLint --fix и снова Prettier: автоисправления ESLint (например, скобки у условий) форматируются в стиле Prettier.

## Задачи

- План работ — [GitHub Issues](https://github.com/bysavelii/cyberzavod/issues): одна задача — один issue с тем, зачем она, что сделать и когда готово. Задачу читать `gh issue view <N> --comments`.
- Одобренную человеком постановку публиковать комментарием к issue (`gh issue comment <N>`).
- Коммит, который закрывает задачу, пишет в теле `closes #N`.
- Выкатка: push в `main`, затем следить за CI (`gh run watch`); красный CI — возврат на доработку. После выкатки открыть изменённые страницы cyberzavod.com в браузере и убедиться, что они работают.

## Общие правила

- TypeScript strict, без `any`. Идентификаторы, комментарии и JSDoc — на английском; названия тестов (`it`, `t.Run`) — на русском.
- **Тексты CLI и адаптера для человека и агента** — только через каталоги сообщений на английском и русском (`packages/cli/src/messages/`, `adapters/claude/src/messages/`, `adapters/codex/src/messages/`, `packages/adapter-kit/src/messages/`); язык выбирает CLI: `--lang`, `CYBERZAVOD_LANG`, локаль системы, английский. Строка для человека в коде вне каталога — ошибка ревью. Исключения: диагностика формата, которую печатают как есть (тексты `parse…` ядра, хранилища и адаптера, на английском), тексты генерируемых файлов (`generate/`, `starterRules`: они всегда английские), содержимое записей и ответы сервера (кроме `unauthorized` и `limit_reached`). Тексты сайта — через словарь `UI_TEXT` (см. `apps/web/AGENTS.md`).
- В журнал и в репозиторий не должны попадать ключи, токены, пароли, адреса серверов и личные данные. Сырые журналы и черновики лежат в `capture/` журнала и в git не идут. Исключение — учётка локальной базы в `compose.yaml` и `.devcontainer/compose.yaml`: она только для разработки, порты привязаны к 127.0.0.1, в продакшене пароли берутся из `.env` на сервере.
- Небольшие коммиты в формате [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `<тип>(<область>): <описание>`. Тип и область на английском (`feat`, `fix`, `docs`, `test`, `refactor`, `ci`, `chore`, `build`), описание того, что сделано, — на русском: `feat(core): добавлен проигрыватель записи`. Области: `core`, `storage`, `cli`, `harness`, `adapter-claude`, `adapter-codex`, `adapter-kit`, `journal`, `web`, `api`, `deploy`, `ci`, `hooks`. Ломающие изменения — `!` после типа и футер `BREAKING CHANGE:`.
