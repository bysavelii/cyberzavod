# CLI (packages/cli)

`cyberzavod` — npm-пакет и точка входа для человека: подключает проект (`npx cyberzavod init`), держит файлы агента в согласии с harness и конфигом, пишет решения и заметки в журнал, а командой `hook` исполняет хуки агента. Сам агентов не запускает; в сеть ходит публикация записей (`login`, `share` и соседние команды) и первый `view` (за пакетом цеха), остальное работает локально.

## Правила

- **Адаптеры агентов** (`src/agents/`). Всё, что командам нужно от агента, — интерфейс `AgentAdapter` (`agent-adapter.ts`); его определяет CLI, а пакет адаптера о CLI не знает. Объект адаптера собирается в CLI поверх пакета (`agents/claude.ts`) и лежит в `registry.ts` (`createAdapters`, `Adapters` — запись по `AgentName`, пропущенный агент не соберётся). Только `agents/claude.ts` вызывает функции `@cyberzavod/adapter-claude` (`previewClaude`, `syncClaude`, `disconnectClaude`, `inspectClaudeHooks`, `draftSession`, `publishSessions`, `previewDrafts`, `runHook`), и только `agents/codex.ts` — функции `@cyberzavod/adapter-codex` (`previewCodex`, `syncCodex`, `disconnectCodex`, `inspectCodexHooks`, `draftSession`, `publishSessions`, `previewDrafts` и работа с доверием); запрос `draft`/`publish`/предпросмотра черновиков в параметры адаптеров переводит `agents/session-requests.ts` (сообщения кита нужного языка); команды зовут методы адаптера. Различия агентов в текстах — `adapter.terms` (`AgentTerms` в каталоге сообщений: название продукта и вызов скилла, `/setup` у Claude Code и `$setup` у Codex): текст, где названо имя агента или скилла, берёт их из `terms`, а не пишет в строке. В интерфейсе «посмотреть» и «сделать» — разные методы (`inspectFiles`/`syncFiles`, `planDisconnect`/`disconnect`), а не флаг `check`. **Подключённые агенты проекта** (`agents/host-agent.ts`) — ключи `agents` в `.cyberzavod/project.json`, в порядке подключения: `connectedAgentsOf(config)` — пусто означает `claude`, неизвестное имя — `CommandError` `unsupportedAgent` со списком поддерживаемых; `connectedAdaptersOf(config, adapters)` — их адаптеры; `agentNamesOf(config)` — те же имена без проверки (для `status`, который печатает и такой конфиг). Провайдера проверяет сам адаптер. Команды, которым нужен один агент (`draft`, `publish`), берут `adapterNamed(config, adapters, --agent)`: без флага при нескольких агентах — `CommandError` `agentRequired`, агент не из подключённых — `agentNotConnected`; `sync`, `doctor`, `status`, `view`, `disconnect` работают со всеми подключёнными. `adaptersAt(каталог, adapters)` — терпимый вариант для `doctor`: без проекта и с битым или неподходящим конфигом возвращает адаптер по умолчанию. `hook` выбирает адаптер флагом `--agent` (`agentNamed` в `host-agent.ts`: без флага — `DEFAULT_AGENT_NAME`, неизвестное имя — `CommandError` `unknownAgent`), а не конфигом проекта: команду хука пишет сам адаптер в свой файл хуков и знает, чей он, а хук остановки обязан отпускать агента с сообщением и при битом конфиге, так что разбор хука через конфиг ему не годится; `draft` и `publish` выбирают адаптер флагом `--agent` (`adapterNamed`). `createAdapters(источник)` получает окружение и домашний каталог (для конфига Codex). **Конфиг человека** (`AgentAdapter.userConfig`, `UserConfigAccess`; у Claude — `undefined`): Codex запускает хуки проекта, только если конфиг самого человека им доверяет. `init` строит план (`planConnect`) до сводки, показывает в ней строки «доверит проект / одобрит хуки», пишет после единственного подтверждения; `sync` только переносит уже данное доверие на новые хуки (`carryOver`) и не создаёт его; `sync --check` состояние машины не смотрит; `doctor` проверяет его (`doctor/trust.ts`, проверка `trust`); `disconnect` забирает назад только то, что добавил Cyberzavod, и называет доверие, оставленное человеку. Сломанный конфиг — ошибка до первой записи. Новый агент — новый член `AGENT_NAMES`, объект в `agents/` и строка в `registry.ts`. **Выбор агента.** `init --agent <имя>` (по умолчанию `claude`) пишет агента ключом в `agents` с настройками его этапов.
- **Команды** — таблица `COMMANDS` в `cli.ts` (`Record<CommandName, Command>`): раздел справки (`section`), обработчик, который сам разбирает свои флаги `parseArgs`; справка команды лежит в каталоге сообщений: строка вызова `usage`, короткий `summary` (одна строка списка, до 80 символов с отступом) и `parameters` (флаги, аргументы, переменные окружения). Общая справка (`help.ts`, `--help`) — команды по разделам (`COMMAND_SECTIONS`) в один экран; команды с `section: "service"` (`hook`, `draft`, `publish`) вне списка. `<команда> --help` или `-h` до `--` печатает справку команды и не запускает её (для любой, включая служебные). `--version` (`-v`) печатает голую версию пакета (`HARNESS_VERSION`). Неизвестная команда — ошибка в stderr с кодом 1: с ближайшей видимой командой (расстояние Левенштейна ≤ 2, `closest-name.ts`) и указанием на `--help`. Новая команда — новое имя в `COMMAND_NAMES`, справка в `en.ts` и `ru.ts` (без неё не соберётся `tsc`), строка таблицы с `section` и файл в `src/commands/`. `runCli(argv, directory, env)` получает окружение явно, `process.env` внутри `cli.ts` не читается. Ожидаемая ошибка (`EXPECTED_ERRORS`: `CommandError`, `ApiError`, ошибки конфига, журнала и записи; ошибки `parseArgs`; ошибки адаптера узнаёт и описывает сам адаптер — `describeError`) печатается одной строкой с кодом выхода 1; остальное — исключение.
- **Сообщения и язык** (`src/messages/`). Всё, что CLI говорит человеку, лежит в каталогах `en.ts` и `ru.ts` (тип `CliMessages` в `cli-messages.ts` по разделам; значение — строка или функция, при двух и более параметрах — один объект с именованными полями; `CLI_MESSAGES` в `catalog.ts`). Язык (`language.ts`): флаг `--lang <язык>` или `--lang=<язык>` в любом месте до `--`, затем `CYBERZAVOD_LANG` (неподдерживаемое значение пропускается: опечатка не должна ронять хуки), затем локаль по POSIX (первая непустая из `LC_ALL`, `LC_MESSAGES`, `LANG`; язык — часть до `_`, `.`, `@`, `-`; `C` и неподдерживаемые — английский), затем английский; неподдерживаемый `--lang` — ошибка с кодом 1 на языке без флага. Печатающая функция получает `messages: CliMessages` параметром. Ошибка для человека — `CommandError`, она хранит не строку, а `LocalizedText<CliMessages>`: `new CommandError((messages) => messages.errors.…)`; текст на нужном языке выбирает `runCli` при печати (`describe`), а `message` ошибки всегда английский. Адаптеру CLI передаёт язык (`language` в запросах `runHook`, `draftSession`, `publishSessions` и в `ProjectContext` проверок), а набор сообщений (`KIT_MESSAGES[язык]` для хуков, черновика и публикации, `CLAUDE_MESSAGES[язык]`/`CODEX_MESSAGES[язык]` для ошибок адаптера) выбирает объект адаптера в `agents/`. Не переводятся: диагностика формата файлов (тексты `parse…` ядра, хранилища и адаптера: `RecordError`, `ProjectFileError`, `JournalError`, `DraftError` из `parseDraft` и соседи) — она на английском, CLI печатает её как есть после переведённой рамки; тексты генерируемых файлов, заготовка правил `init` (`starterRules`) и названия этапов из harness — всегда английские, при любом языке CLI.
- **Каталог проекта** — `INIT_CWD` (его ставят pnpm, npm и npx) или текущий; у `hook` каталог проекта выбирает адаптер (у Claude — `CLAUDE_PROJECT_DIR`, у Codex — `cwd` из нагрузки хука, адаптер поднимается от него до маркера: Codex не даёт хуку переменной с корнем проекта); команды, кроме `init`, поднимаются от него до маркера `.cyberzavod/project.json`.
- **`init`** (`commands/init.ts`) — распознавание проекта (`detect.ts`), начальный конфиг (`initial-config.ts`: найденное, процесс `default`, агент на каждый этап с ролью и модель `default` — их в `init` не спрашивают, правят в `.cyberzavod/project.json`), короткая сводка того, что найдено и что появится, одно подтверждение «Продолжить? [Y/n]», затем конфиг, AGENTS.md, строка `capture/` журнала в `.gitignore` (если журнал в проекте) и `sync`; итог называет, что закоммитить. Тонкая настройка — флагами: `--id` (нормализуется), `--check` (повторяемый, целиком заменяет найденные проверки), `--journal` (путь от корня проекта, не абсолютный), `--yes`/`-y` (без вопроса). Пустые значения и абсолютный `--journal` — `CommandError` до сводки. Распознанное — подсказки и справочный `stack`, а не ограничения: флаги их перекрывают. Отказ (любой ответ, кроме согласия, и конец ввода) ничего не пишет и выходит с кодом 0. До сводки `init` проверяет файлы агента (`previewFiles` адаптера): если чужой файл стоит на месте сгенерированного, — `CommandError` `initBlocked`, и ничего не записано, даже конфиг. Повторный `init` идемпотентен: в уже подключённом проекте он ничего не пишет и печатает «конфиг в порядке» и либо «файлы актуальны, делать нечего» (код 0), либо «запустите `npx cyberzavod sync`» (код 1). **Второй агент** — `init --agent <имя>` в проекте, где этого агента нет среди подключённых (`addAgent` в `commands/init.ts`): до сводки проверяются его файлы (`previewFiles`; чужой файл на месте сгенерированного — `initBlocked`, ничего не записано) и план доверия в конфиге человека, сводка называет его файлы и доверие (`init.addAgentTitle`), одно подтверждение, затем `sync` файлов уже подключённых агентов (он переводит манифест на версию 2 до того, как новый агент допишет свою секцию), файлы нового агента, в конце — конфиг с `agents.<имя>` и доверие. Отказ ничего не пишет. В проекте без агентов в `agents` подразумеваемый `claude` записывается в конфиг явно. Рукописный `CLAUDE.md` становится `AGENTS.md`, иначе AGENTS.md пишется из `templates/rules.md`: каждая заглушка заготовки (строка форматирования, абзацы «Tasks» и «Code and tests», пустой список проверок) несёт отметку `RULES_TODO_MARK` из ядра (в шаблоне — `{{todo}}`), её заменяет скилл `/setup`.
- **Распознавание** — таблицы маркеров (`LANGUAGE_MARKERS`, `LOCKFILES`, `FRAMEWORK_DEPENDENCIES`, `LANGUAGE_VERIFICATION`): новый язык или фреймворк — новая строка таблицы, а не условие.
- **Подтверждение** идёт через интерфейс `Confirmation` (`confirmation.ts`): `terminalConfirmation` для человека в терминале, `confirmWithoutAsking` для `--yes` и запуска без терминала (`process.stdin.isTTY !== true`: облако, CI, pipe) — там вопрос не задаётся. `init` не читает stdin сам.
- **`sync`** передаёт генерацию адаптерам всех подключённых агентов (сначала файлы всех проверяются на чужие, потом пишутся конфиг и файлы каждого по порядку), удаляет CLI, который клали в проект прежние версии (`LEGACY_TOOL_FILE`, `commands/legacy-tool.ts`; пока он на месте, `--check` выходит с 1) и пишет в конфиг версию harness (`HARNESS_VERSION` в `installation/installation.ts`, она же версия npm-пакета — это проверяет тест) и `stack`; `sync --check` только сообщает о расхождениях и выходит с 1 — его запускает `make check-web`; `sync --diff` печатает тот же план («добавит / обновит / удалит / ваши / исправлены руками / не тронет никогда») и выходит с 0. Без `--force` `sync` сначала строит план и при конфликте падает до записи конфига. **Владение файлом** решает адаптер (манифест `.cyberzavod/generated.json`): Cyberzavod не перезаписывает молча файл, который не его или исправлен руками, — ни в `init`, ни в `sync`, ни в `disconnect`.
- **`disconnect`** (`commands/disconnect.ts`) — `disconnect [--agent <имя>] [--yes]`: план «уберёт / оставит», одно подтверждение, затем `disconnect` каждого подключённого адаптера (свои нетронутые файлы, секция в манифесте, свои хуки и запреты в настройках; манифест удаляется, когда секций не осталось), прежний вшитый CLI и `.cyberzavod/project.json`. С `--agent` при нескольких подключённых агентах убирается только названный (его файлы, хуки, запреты, доверие, его секция в манифесте и `agents.<имя>` в конфиге; остальные агенты остаются подключёнными, прежний вшитый CLI и конфиг проекта не трогаются); `--agent` единственного агента — как без флага. Остаются код, AGENTS.md, журнал, строка `capture/` в `.gitignore` (она защищает сырые журналы, пока они на диске), чужие настройки и хуки, файлы, исправленные руками. Без терминала и без `--yes` — отказ с кодом 1 и ничего не меняется.
- **JSON** (`json-output.ts`): `status --json`, `doctor --json`, `sync --check --json` и `sync --diff --json` печатают один документ `{schemaVersion, command, status, …}` без цвета; ключи стабильны, `schemaVersion` (`JSON_OUTPUT_SCHEMA_VERSION`, сейчас 2) меняется только при несовместимой правке; у этапа в `status --json` — `performers: [{agent, model}]` (у ведущего пустой список). У `doctor` каждая проверка несёт `id`. `--json` у `sync` без `--check` или `--diff` — ошибка.
- **Неожиданная ошибка** печатается одной строкой с подсказкой про `CYBERZAVOD_DEBUG=1`; стек — только с этой переменной.
- **`doctor`** (`commands/doctor.ts`, проверки в `doctor/`) — `doctor [--run-checks] [--json]`: по пункту на проверку, строка `✓` / `✗` / `–`, под `✗` строка «Как починить» с отступом 4, в конце «Всё в порядке.» или «Проблем: N.»; есть `✗` — код 1. Сеть не нужна, ничего не исправляется. Порядок: Node (`MINIMUM_NODE_MAJOR` = `engines.node`, это проверяет тест), git, программа агента (`adapter.programCheck`; у Claude Code — `claude` в `PATH`, нет — `notice`), галерея (токен читается с диска и не печатается; нет входа — `notice`, битый файл — `✗`), конфиг (`configCheck`: проект ищется от каталога вызова, затем `connectedAgentsOf`: неподходящие агенты — `✗` с подсказкой править `agents`, и проект считается ненайденным), хуки (`inspectHooks` адаптера; сверяются с `config.harness`), файлы агента (`inspectProjectFiles` из `sync.ts`, как `sync --check`; при расхождении версий конфига и CLI говорят только о нём), корневой `AGENTS.md` (есть и без `RULES_TODO_MARK` — отметку ядра, своей нет), команды проверок, `.gitignore` (точная строка `captureIgnoreEntry`). Проверки агента (программа, хуки, `trust`) идут по разу на каждого подключённого агента и несут в JSON поле `agent`, `id` у них прежние; `files` — одна проверка по всем агентам. Результат проверки — размеченное объединение `CheckResult` по `status` (`passed`, `failed` с `fix`, `notice` с `hint`), печать и подсчёт — исчерпывающие `switch`; `notice` на код выхода не влияет. Вне проекта печатаются проверки машины и `✗` конфига с `init`, проверки проекта пропускаются. Команды проверок: без `--run-checks` проверяется только «программа найдена» (`programs.ts`: первое слово команды без присваиваний `NAME=value`; слово с `/` или `\` — файл от корня проекта, иначе поиск в `PATH`, на win32 с `PATHEXT`; найденное — файл, на POSIX исполняемый; ничего не запускается, make-цели и скрипты по имени не проверяются, команда, начатая со встроенной командой оболочки, даёт `✗`); с `--run-checks` каждая команда запускается оболочкой в корне (`run-command.ts`), код 0 — `✓`. Реализацию выбирает `cli.ts`, в `runDoctor` флага нет. Проверки агента, которых нет у других, — `adapter.extraProjectChecks`. Новая проверка — новый файл в `doctor/` (`MachineCheck` или `ProjectCheck`), тесты рядом, строка в `machineChecksFor` или `projectChecksWith` и тексты в `DoctorMessages`.
- **Установка** (`installation/`) — harness и шаблоны (ключи шаблонов — `<адаптер>/<имя>`: `cli/rules.md`, `claude/setup.md`, `codex/setup.md`; `Installation.claudeTemplates`, `codexTemplates`). Читает их только `assets.ts`: из исходников — с диска репозитория, а сборка (`scripts/build.ts`, esbuild) подменяет модуль встроенными текстами. Поэтому `dist/cyberzavod.mjs` — один файл без зависимостей (`smol-toml` адаптера Codex попадает в бандл, лицензия — `dist/THIRD_PARTY_LICENSES`; у самого CLI зависимостей нет и в его тестах `smol-toml` не импортируют): его публикует npm, а хуки запускают через npx (команду и запасной путь без сети задаёт адаптер). `init` и `sync` работают и из исходников. `prepare` в `packages/cli` собирает `dist/` при `pnpm install`: так pnpm создаёт `node_modules/.bin/cyberzavod`, и npx находит пакет в этом репозитории. `prepack` только копирует LICENSE: сборку при `npm publish` делает тот же `prepare`. README пакета — свой короткий `README.md` (что это, Quickstart, `doctor`, ссылка на гайд), а не копия корневого: в корневом раздел разработки и относительные ссылки, которые на npmjs.com не работают; подробности живут только в корневом README и гайде, правка Quickstart там — повод сверить короткий. Версия `HARNESS_VERSION` — версия, на которую хуки проекта ссылаются через `npx cyberzavod@<версия>`. Подсказки человеку и генерируемые тексты зовут CLI через `CLI_COMMAND` и `pinnedCliCommand` адаптера (`npx cyberzavod`, `npx cyberzavod@<версия>`).
- **`view`** (`commands/view.ts`, `viewer/`) — `view [--no-open]`: записи (`sessions/` журнала) и черновики (`previewDrafts` каждого подключённого агента: сборки без редактуры, чей `id` ещё не опубликован) проекта в цехе в браузере; в проект и журнал ничего не пишет. Цех лежит в отдельном npm-пакете `@cyberzavod/viewer` (та же версия, что у CLI; `packages/viewer`) и только по этой команде попадает в кэш npx: `init`, `sync`, хуки и сам пакет `cyberzavod` про него не знают. CLI зовёт `npx -y --prefer-offline --fetch-retries=0 --package <спецификация> cyberzavod-viewer` в корне проекта (флаги — `NPX_CACHE_FIRST_FLAGS` кита: пакет берётся из кэша без реестра, без кэша и сети npx падает сразу, это `CommandError` `viewerUnavailable`; на win32 `npx.cmd` идёт через оболочку, спецификация всегда в двойных кавычках, `viewer-package.ts`, `locate-viewer.ts`). Спецификация — `@cyberzavod/viewer@<HARNESS_VERSION>` или `CYBERZAVOD_VIEWER_PACKAGE` (имя, версия или путь к архиву: так `pnpm smoke` проверяет архив до публикации). Пакет цеха — только статика и bin, который печатает путь к своему `dist/`; файлы раздаёт сам CLI (`server.ts` на `node:http`, без зависимостей): слушает только `127.0.0.1` на случайном порту; `Host` должен быть `127.0.0.1:<порт>` или `localhost:<порт>`, иначе 403 (DNS rebinding); только `GET` и `HEAD`, иначе 405; таблица статики строится один раз (`static-files.ts`), путь запроса ищется в ней без декодирования и с диском не склеивается, поэтому `..` и закодированные точки дают 404; API один, без параметров: `GET /api/recordings` → `{published, drafts}` (каждый запрос читает журнал и черновики заново, битый журнал — 500 без причины в ответе и причина в терминале). Браузер открывается системной программой без оболочки (`browser.ts`: `open`, `rundll32 url.dll,FileProtocolHandler`, `xdg-open`); неудача — строка `view.openFailed`, не ошибка. Язык цеха — язык CLI в адресе `/?lang=`. Адрес печатает строка `factory floor: <адрес>` (`цех: …`), её читает smoke. `locate` (npx) и `open` (браузер) — параметры `startView`, чтобы тесты шли без npx и браузера; сервер закрывается после `SIGINT`/`SIGTERM`.
- **Публикация** (`sharing/`, `commands/login.ts`, `share.ts`, `gallery.ts`) — `login`, `logout`, `share <id>`, `unshare <id>`, `gallery [--public | --private]`: вход через GitHub (device flow) и отправка записи сессии в личную галерею на сервер. Сервер принимает `GET /api/auth/github`, `GET /api/me`, `PUT` и `DELETE /api/me/recordings/{id}`, `PUT /api/me/gallery` с заголовком `Authorization: Bearer <токен>` и отвечает ошибкой `{"error", "message"}`; сервер Cyberzavod (`CyberzavodApi`, `HttpCyberzavodApi`) и GitHub (`GithubDeviceAuth`, `HttpGithubAuth`) — за интерфейсами, сеть — встроенный `fetch`, который передаётся в конструктор; все команды получают `Sharing` (`services.ts`: адрес, сервер, GitHub, хранилище токена, пауза), `createSharing` собирает настоящий, тесты подставляют заглушки из `sharing/fixtures.ts`. Адрес сервера — `CYBERZAVOD_API_URL`, по умолчанию `DEFAULT_API_URL` (`https://cyberzavod.com`). Токен — `credentials.json` (`{"token": "..."}`) в `$XDG_CONFIG_HOME/cyberzavod`, `~/.config/cyberzavod` или `%APPDATA%\cyberzavod`, права 0600 (`settings.ts`; путь — чистая функция от env и платформы); токен не печатается, не попадает в сообщения ошибок и в журнал. Запись перед отправкой читается из `sessions/` журнала проекта (тот же `requireProjectAt`) и проходит `parseRecord` ядра: сервер проверяет конверт, размер и длины полей — по тем же пределам ядра (`RECORD_LIMITS`), так что слишком длинное поле отклоняется до отправки с причиной от ядра. Ошибка сервера — `ApiError` (код и текст из ответа, язык выбирает сервер) и печатается как ожидаемая; `unauthorized` превращается в просьбу войти заново, `limit_reached` — в список записей с командой `unshare`, оба с текстом из каталога сообщений. Неожиданный ответ сервера и статус без тела ошибки — `CommandError` из каталога, а не `ApiError`. Вывод этих команд читает скилл `/publish-recording` (шаблон адаптера) и по тексту строк узнаёт состояние: `login` печатает адрес и код до первого опроса GitHub (скилл запускает его в фоне и показывает код человеку), затем `signed in: <логин>`; `share` — `recording <id> sent|replaced` и `link: <адрес>`, при закрытой галерее — `the gallery is closed…`; `gallery --public` — `Gallery page:` и `README badge:`. Строки про вход, ссылку, закрытую галерею, бейдж и `limit_reached` (ошибки входа тоже) меняют только вместе с шаблоном. Остальные команды ничего не отправляют.
- **Дымовая проверка пакета** (`scripts/smoke.ts`, `pnpm smoke`): `npm pack` (в архиве только `LICENSE`, `README.md`, `package.json`, `dist/cyberzavod.mjs`, `dist/THIRD_PARTY_LICENSES`, и распакованный размер не больше `CLI_UNPACKED_BUDGET_BYTES` = 600 000 Б: так в пакет не попадут цех и Pixi), `npm pack` пакета цеха (`LICENSE`, `README.md`, `package.json`, `bin/cyberzavod-viewer.mjs`, `dist/index.html`, `dist/THIRD_PARTY_LICENSES`, `dist/assets/*`, без `dependencies`), установка архива CLI во временный каталог и путь человека в проекте с пробелом в пути: `init --yes`, `status`, `doctor --json`, `sync --check`, повторный `init`, хук `record`, `decision`, `view`, `disconnect`; после него код, AGENTS.md, журнал и настройки человека должны остаться как были. Шаг `view` (путь Claude Code): в проект кладутся запись `sessions/smoke-view.json` и неотредактированный черновик `capture/claude/drafts/smoke-draft.json`, `view --no-open` запускается дочерним процессом с `CYBERZAVOD_VIEWER_PACKAGE=<архив цеха>` и временным `npm_config_cache`; по строке `factory floor:` берётся адрес, `/` отдаёт страницу, `/api/recordings` — одну запись и один черновик, пути с `..` (в том числе закодированные) дают 404, чужой `Host` — 403; после остановки (SIGINT, код 0) файлы проекта те же, `node_modules` в проекте нет, цех лежит в `_npx` временного кэша; второй запуск с `npm_config_offline=true` тоже отдаёт `/` (архив — локальный файл, так что это не доказывает кэш npx: спецификацию из реестра проверяют руками по `RELEASING.md`). Тот же архив проходит вторым путём — для Codex (`init --yes --agent codex`): временные `CODEX_HOME`, `XDG_CONFIG_HOME` и `APPDATA` (настоящий домашний каталог не трогается), заранее написанные пользовательские `config.toml` и `hooks.json`; проверяется, что `init` дописал доверие в конфиг человека, а хуки `record` и `guard` отвечают правильно из корня проекта и из подкаталога `src` (smoke зовёт подкоманду `hook` установленного CLI напрямую; сгенерированную команду `sh -c 'npx --prefix …'` целиком запускает только e2e адаптера), повторный `init` ничего не меняет, а `disconnect` возвращает конфиг и хуки человека в прежний вид. Третий путь — «Claude Code, затем Codex» (`init --yes`, затем `init --yes --agent codex`, тоже во временном `CODEX_HOME`): файлы Claude Code не меняются, в манифесте две секции, `sync --check` и `doctor --json` (хуки обоих агентов с полем `agent`) зелёные, `status --json` называет исполнителей обоих; `disconnect --agent codex` возвращает конфиг и хуки Codex человека и оставляет Claude Code, затем `disconnect` возвращает проект к файлам человека. Только API Node без оболочки (кроме вызова `npm`): CI гоняет её на Linux, macOS и Windows с Node 22 и 24 (job `package`) и перед публикацией.
- **Выпуск** — тег `vX.Y.Z` (совпадает с `version` обоих пакетов, `cyberzavod` и `@cyberzavod/viewer`): CI проверяет, гоняет дымовую проверку и публикует в npm сначала цех, потом CLI (уже опубликованную версию пропускает) (`.github/workflows/release.yml`); порядок — в `RELEASING.md`.
- Пути — через `node:path`; в выводе — пути от корня проекта, а не абсолютные.
- Тесты публикации — без сети: заглушки `CyberzavodApi` и `GithubDeviceAuth`, `memoryCredentials`, а HTTP-слой — с подменённым `fetch`; ожидание входа — с мгновенной паузой `sleep`.
- Тесты — на временном каталоге и заготовленном `Confirmation`; вывод проверяется по перехваченному `console`.
