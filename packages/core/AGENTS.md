# Ядро (packages/core)

Чистый TypeScript: единая модель Cyberzavod — этапы и процесс, агенты этапов, конфиг проекта, модель harness, записи журнала и граница хранилища `RecordStore`. На этой модели стоят CLI, хранилище, адаптеры агентов, проигрыватель цеха и сайт; другой модели данных нет.

## Правила

- Ни DOM, ни фреймворков, ни внешних зависимостей. Код должен работать одинаково в браузере, в Node и в тестах.
- Участник разговора (`Speaker`) — рабочий этапа или `foreman`, мастер: человек-программист, который раздаёт задачи и принимает итог. Реплика (`message`) — это `from` и `to` (оба `Speaker`, не равны друг другу), одна строка `line` для цеха и полный `text` для журнала. Вмешательство человека (`intervention`: `reason`, `line`, `text`) устроено так же: `line` для цеха, `text` для журнала; причина (`INTERVENTION_REASONS`: `question`, `plan_review`, `rework_limit`, `stop_gate`) — то, что остановило автоматику, а не то, что решил человек. Цеху полный текст не нужен и в страницу с цехом попадать не должен: `briefOf` превращает `SessionRecord` в `BriefSessionRecord` без `text` у реплик и вмешательств, и `buildScript`, `summarize` и проигрыватель (`packages/player`) принимают его. Полная запись нужна только журналу.
- **Запись журнала** (`record.ts`) — одна модель на всё: конверт `{version, type, id, timestamp, projectId, sessionId?, source, data}` и размеченное объединение `JournalRecord` по `type`: `session` (сессия агента: `data.title`, `language`, `workflow`, `harness`, `events`), `decision` (`title`, `description`) и `note` (`text`). `source` — `{type: "agent", provider, agent}` или `{type: "manual"}`. Версия конверта — `RECORD_VERSION`; другие версии не принимаются: старые журналы переведены один раз, слоёв совместимости нет. Новый тип записи — новый член объединения, ветка в `parseRecord` и коллекция в хранилище. Новые типы событий сессии версию не меняют, если только добавляются. `data.language` — язык оригинала записи, код ISO 639 (`isLanguageCode`): запись не переводится. Журналы, записанные до этого поля, лежат и в чужих проектах, поэтому запись без него разбирается с `LEGACY_SESSION_LANGUAGE` (`ru`), а не отклоняется. `data.task` — необязательная метка задачи (правило как у `id`, потому что идёт в адрес страницы): записи с одной меткой — прогоны одной задачи, сайт показывает их рядом. `model` на `stage_enter` — необязательный id модели, которая вела этап. Оба поля необязательны: записи без них валидны, версия не меняется. Предикаты `isRecordId`, `isHarnessVersion` и `isLanguageCode` общие для ядра и пишущего записи кода.
- **Токены** (`record.ts`): `usage` — именованный `UsageEvent` `{t, type, tokens, model?, breakdown?}`. `breakdown` (`TokenBreakdown`) делит токены на виды по колонкам таблиц цен: `input` (вход без кэша), `output`, `cacheRead`, `cacheWrite5m`, `cacheWrite1h`; все пять — целые неотрицательные (`Number.isSafeInteger`), лишние ключи отбрасываются, неполная разбивка — `RecordError`. `model` — id модели, которая потратила токены (правило как у `model` на `stage_enter`). `tokens` — счётчик: при разбивке он обязан равняться `countedTokensOf(breakdown)` = вход + выход + запись в кэш (чтение кэша не считается); это единственное место правила счётчика, иначе `RecordError`. `addBreakdowns` и `NO_BREAKDOWN` — сумма разбивок для кода, который складывает токены по модели. Оба поля необязательны: записи без них (все прежние) валидны, версия не меняется.
- **Пределы длины** (`record-limits.json`, экспорт `RECORD_LIMITS`): `idLength` 100 — `id`, `projectId`, `data.task`; `lineLength` 500 — `sessionId`, `source.provider`, `source.agent`, `data.title`, `workflow`, `harness`, `goal`, каждое из `requirements`, `model` у `prompt`, `stage_enter` и `usage`, `line` у `message` и `intervention`, `reason` у `stage_fail`; `textLength` 20 000 — `text` у `message` и `intervention`. Длина считается в кодовых точках Unicode (`[...value].length`), эмодзи — один символ; превышение — `RecordError` вида `<поле> must be at most <N> characters` (для события — с `event #N:`), его бросает `parseRecord`, так что пределы соблюдают все пути: `share`, `publish`, сборка сайта и разбор записи на `/r/`. Числа лежат только в этом JSON (импорт с атрибутом `with { type: "json" }`: Node без сборки его требует); сервер галерей (`apps/api/internal/gallery/limits.go`) держит копию, которую сверяет `TestLimitsMatchCore`. Решения и заметки пределов не имеют: в галерею они не попадают.
- **Процесс и проект.** `STAGES` (`stage.ts`) — этапы в порядке процесса по умолчанию: `planning`, `implementation`, `review`, `verification`, `record`; новый этап — новая строка здесь, станок в планах цеха и скилл harness с `stage` в `metadata`. `Workflow` — имя и этапы по порядку. `AgentConfig` (`agent.ts`) — настройки исполнителя этапа: `provider` и `model`, оба необязательные; ядро не знает ни одного провайдера и агента, сочетания проверяет адаптер. `ProjectConfig` (`project-config.ts`) — `.cyberzavod/project.json`: `projectId`, `harness`, `workflow`, `journal` (путь журнала от корня через `/`), `agents` (имя подключённого агента → `StageAgents`, настройки по этапам; порядок ключей — порядок подключения, имена ядро не проверяет; `PROJECT_CONFIG_SCHEMA_VERSION = 2`. Конфиг версии 1 (поле `schemaVersion` нет или 1) читается: этапы с одним названным агентом становятся его секцией, без названного — `{}`, с двумя разными — `ProjectConfigError`; на диске он становится версией 2 при первой записи `sync`), `verification` (`commands` и `paths`) и справочный `stack`. `skill.ts` — подмножество формата [Agent Skills](https://agentskills.io/specification), которым пользуется harness: `parseSkillDocument` читает SKILL.md (`name` и `description` по правилам спецификации, плоская `metadata` строк, другие поля — `SkillError`), `skillFrontmatter` пишет шапку обратно (поля агента — `agentFields` — как есть после описания), `yamlString` берёт строку в кавычки, только если YAML прочитал бы её иначе. `harness.ts` — модель harness из скиллов `skills/<имя>/` и процессов `workflows/`: `parseHarness` (`HarnessFiles`: путь от корня harness → текст) собирает ведущего (`LEAD_SKILL`, `feature`), остальные скиллы (`skills` — адаптер кладёт их в проект как есть), этапы (`StageGuide`: скилл с `stage`, `title`, `role` и `access` в `metadata`; ровно один скилл на каждый из `STAGES`) и принципы (`PRINCIPLES_SKILL`: файлы `references/*.md`, на каждый должна быть ссылка в инструкциях скилла; `always-on` в `metadata` отмечает принципы, которые действуют всегда — `isAlwaysOn`). Рядом с SKILL.md — только Markdown: файлы идут в проект с отметкой генерации. Файлы читает хранилище или их встраивает сборка CLI.
- **Языки интерфейса** (`interface-language.ts`): `INTERFACE_LANGUAGES` (`en`, `ru`), `InterfaceLanguage`, `DEFAULT_INTERFACE_LANGUAGE` (`en`), `isInterfaceLanguage`, обобщённые `MessageCatalog<Messages>` (набор сообщений на каждом языке, язык без набора не компилируется) и `LocalizedText<Messages>` (текст, язык которого выбирается при показе). Тексты и чтение окружения — в CLI и адаптере, в ядре их нет; диагностика формата (`parse…`, `RecordError` и соседи) по-прежнему на русском и не переводится.
- **Заготовка правил** (`project-rules.ts`): `RULES_TODO_MARK` — отметка заглушки в заготовке AGENTS.md. Один источник для заготовки `init`, скилла `/setup` (заменяет строки с отметкой) и проверки `doctor` (отметка в корневом AGENTS.md — ошибка): пока отметка есть, заготовка не заполнена.
- **Хранилище** — интерфейс `RecordStore` (`list`, `write`); реализации (каталог на диске) живут вне ядра.
- Карточка проекта (`Project<Language>`: `id`, `name` и `description` — по строке на каждый язык витрины, необязательные `repo` и `website` по https и `stack` — список из 1–6 подписей вроде «TypeScript», без перевода) — то, что сайт показывает о проекте; `parseProject(raw, languages)` проверяет её так же, как `parseRecord` запись. Список языков передаёт витрина: ядро не знает, на каких языках сайт. Как проект собирать — `.cyberzavod/project.json` в его репозитории, в ядро это не входит. Общие предикаты формата (`isObject`, `isLine`) — во внутреннем `guards.ts`, наружу не идут.
- Данные извне (JSON записи) проходят через `parse…` и становятся типизированными; дальше по коду гуляют только проверенные типы.
- События записи — размеченное объединение по полю `type`. Новый тип события добавляется в объединение, в `parseSessionEvent` и во все исчерпывающие `switch`, на которые укажет компилятор.
- **Возвраты** (`rework.ts`): `reworksOf(session)` — единственное место, где выводятся возвраты сессии и то, что сказал этап, возвращая работу. Один `Rework` на каждый `stage_fail`, по порядку событий: `t`, `stage`, `reason` и `message`. `stage_fail.reason` всегда общий («review sent the work back»), суть — в реплике: `message` — последняя реплика с `from` этого этапа, найденная назад по массиву событий (не по `t`; кому она адресована — не важно). Поиск останавливается на `stage_enter` того же этапа или на предыдущем `stage_fail` того же этапа, чтобы реплика прежнего прохода не попала в этот возврат. Этап промолчал — `message` `undefined`, и показывают запасной `reason`. Реплика отдаётся тем же объектом из `events`. Счётчик `tally`/`summarize` считает те же `stage_fail`, так что число возвратов совпадает.
- **Модели этапов** (`stage-models.ts`): `stageModelsOf(session)` — единственное место, где выводятся модели этапов сессии: этапы, в которые она входила, в порядке `STAGES`, у каждого модели по порядку входов без повторов (доработка может уйти на другую модель). Вход без `model` модель не добавляет. Агент этапа здесь не выводится: проект ведёт один агент, поэтому агент всех этапов записи — её `source`.
- **Цены моделей** (`model-prices.ts`): единственное место, где лежат цены, — таблица `MODEL_PRICES` в USD за миллион токенов по пяти видам разбивки; наружу идёт только `PRICES_AS_OF` — дата сверки с официальной страницей (источник — ссылка в комментарии над таблицей). Только текущие цены, строки без дат: цена почти всегда меняется вместе с новым id модели, а новый id — новая строка, старые записи он не трогает. Если цена существующего id изменилась, строку не правят, а добавляют строки с датой начала действия, и `priceOf` выбирает по `timestamp` записи, иначе старые записи посчитаются неверно. `priceOf` ищет по точному id, затем по id без суффикса снимка `-YYYYMMDD` (`claude-sonnet-4-5-20250929`). Не учитываются fast mode, `inference_geo`, batch; Sonnet 4.5 стоит по базовой цене, хотя в бете 1M на запросах длиннее 200K дороже. Haiku 5.5 в таблице нет: его цена зависит от длины каждого запроса, а по сумме токенов её не восстановить. Строк OpenAI нет, пока цены не подтверждены: стоимость записи Codex неизвестна. Таблицу сверяют руками при каждом выпуске (`RELEASING.md`).
- **Стоимость** (`cost.ts`): `costOf(session)` — единственное место, где выводится стоимость записи в USD по ценам API (не то, что заплатил человек: подписка оплачивается иначе). Результат — `SessionCost`: `total`, `beforeStages` и `stages`. `Cost` — `known` с `usd` или `unknown` с причиной (`no_usage`, `no_breakdown`, `no_model`, `unpriced_model` с id модели): неизвестная стоимость — не ноль, цена не выдумывается и модель этапа вместо модели `usage` не подставляется, потому что токены ведущего в этапе потратила модель сессии, а не станции. Этап `usage` — этап последнего `stage_enter` перед ним по массиву событий (не по `t`); `usage` до первого `stage_enter` — `beforeStages`. `stages` — этапы, в которые запись входила, в порядке `STAGES`, этап без `usage` стоит $0. Часть неизвестна, если неизвестно хоть одно её `usage`; `total` — сумма `beforeStages` и этапов, неизвестен, если неизвестна любая часть или в записи нет `usage`.
- Функции чистые: на вход запись или момент времени, на выход значение. Состояние и время — параметры, а не глобальные переменные.
- Наружу — только то, что экспортирует `src/index.ts`.
- Тесты — Vitest, файлы `*.test.ts` рядом с кодом.
